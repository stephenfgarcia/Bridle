# Proposal: Keel

_Angle: Extensibility and scale first. One deterministic Rust core behind registries and traits (element kinds, analysis kinds, code packs), a tenant-partitioned shell with the region/cell seam reserved from day one, content-addressed pins on every submission and grade, and a staged grading pipeline whose growth points (new deliverable kinds, packs, judge routes, event consumers) are data and plugin registrations rather than rewrites. Every seam ships at MVP with exactly one implementation plus a conformance test, so the MVP stays buildable by a 3-4 person team._

## Summary

Keel is a single-cell, multi-tenant web platform whose spine is one Rust core (engine, checks, canonicalization, scenario, fingerprint) compiled into two content-addressed WebAssembly artifacts, engine.wasm and checks.wasm, that the same TypeScript host runs inside a browser Web Worker and inside Node worker_threads on the server, so the live loop and the authoritative regrade execute identical bytes and bit-identical results are a property, not a tolerance. Everything that will grow is a registry over data or a trait over code: element kinds and analysis kinds are registries inside bridle-fem (frame12, truss, spring at MVP; shell and diaphragm slots reserved); code packs are immutable data bundles plus small pure Rust modules behind two traits, LoadsPack and ResistancePack, with a conformance suite that includes a partial-factor fixture pack so the second pack (NSCP 2015 or Eurocode) is a new crate and bundle, not a redesign. Tenancy is tenant_id plus Postgres row-level security on every row, a reserved tenant.region column and a CellContext factory for storage, queue and LLM clients, so an EU region is a second OpenTofu stack and a tenant directory, not a data migration. Identity is a provider registry (password, Google and Microsoft OIDC, TOTP/passkey MFA at MVP; SAML and LTI 1.3 slots) behind one session model. The grading pipeline is five idempotent, content-addressed stages (intake, analysis, rules, judge, aggregate) on BullMQ with priority lanes and per-tenant caps, so a new deliverable kind, pack or judge route changes a stage input rather than the pipeline. The shell is deliberately boring: Next.js with react-three-fiber for the workspace, a Fastify API with Zod-generated OpenAPI and a generated client, Postgres 16 with JSONB pin columns and generated hash columns, Redis/BullMQ, S3 for every blob (model revisions, result sets, evidence, encrypted prompts, WORM audit), and the Anthropic SDK with structured outputs and prompt caching (claude-opus-5-5 judge and narrative, claude-haiku-5-5 screen). One schema package (bridle-schema@1.0.0, canon/1: Z-up, XZ plane for 2D, SI quanta, RFC 8785 JCS, SHA-256) is built first and no other code hashes anything. Every submission and grade carries the DM pin set (ArtifactRefs for engine, checks, packs, clauses, sections, materials, cost model, rubric, prompt, judge schema, grader) so regrades are new versions with a reason, and the artifact registry can move pins per task without touching published versions. All events use one CloudEvents envelope through a transactional outbox; gradebook, progress, mastery, analytics and the future xAPI projector are consumers, which is the seam for NATS or Kafka later. Present in the schema but stubbed at MVP: shells, regions and constraints; modal, buckling and P-delta; team ownership and lock epochs on ops; SAML and LTI providers; the EU cell; the native Tier-3 solver path; the Eurocode and NSCP pack slots. The MVP build is 17 steps and about 89 engineer-weeks, schema, core and US packs first because every later step pins them.

## Data model

**Tenancy:** Every tenant-owned table carries tenant_id with a Postgres RLS policy (CI test fails if any such table lacks one); the API opens one transaction per request and runs SET LOCAL app.tenant_id and app.actor_id from the session, the app role has no BYPASSRLS, migrations run under a separate role; users are global rows reached only through membership and role_assignment; object storage keys are tenants/{ten_id}/... served by signed URLs (<= 15 minutes); per-tenant KMS keys for analytics pseudonyms; tenant.region (default us) selects a CellContext (db, redis, s3, kms, llm inference geo) so an EU cell is a second stack instance plus a tenant directory; cross-tenant comparison (similarity, catalogs) never happens at MVP; a two-tenant authorization suite exercises every route as every role in CI.

**Storage:** Postgres 16 (RDS Multi-AZ, PITR, UUIDv7 generated app-side; JSONB pin columns with generated columns for model_hash, result_hash, pinset_id; UPDATE/DELETE revoked on content-immutable tables plus triggers); S3-compatible object storage for every blob (model revisions and op segments by hash, result sets, evidence sets, encrypted prompt/response logs, attachments, snapshots, diagnostic bundles, artifacts by digest, audit WORM bucket with Object Lock, backups replicated cross-region); Redis 7 (BullMQ queues, rate limits, sessions cache, exam session registry, presence, result-cache index); IndexedDB in the browser for autosave and unsent ops; all quantities stored in SI base units.

## Structural model schema

packages/schema is the first artifact built and the only source of truth for shared types. Rust structs in crates/bridle-canon (schemars) emit JSON Schema draft 2020-12 files checked into packages/schema/json (bridle-model, bridle-ops, bridle-scenario, bridle-result, bridle-evidence, bridle-deliverables, bridle-task, bridle-rubric, bridle-pinsets, bridle-events, bridle-integrity, bridle-exam); json-schema-to-typescript and json-schema-to-zod generate TS types and zod validators for the API and web; a CI diff gate fails when the emitted schema changes without a version bump. Schema id bridle-schema@1.0.0 with semver (minor additive, readable by N-1 consumers for 90 days) and a separate canon version (canon/1) covering the semantic allowlist, quanta, ordering and header; changing any of those bumps canon and never rewrites stored hashes. Model document: schemaVersion, id (mdl_), settings {mode: 3d|planar-xz (Y=0 enforced)|planar-xy reserved, gravity [0,0,-9.80665], mergeTolerance 0.001 m}, materials[], sections[] (catalog ref sections:aisc-shapes-v16 label or parametric or custom with props A, Iy, Iz, J, Cw, Sy, Sz, Zy, Zz, ry, rz, Asy, Asz, outline), nodes[] {id n_, x, y, z, levelId}, levels[], members[] {id m_, kind frame|truss (shell and link kinds registered later), nodeI, nodeJ, sectionId, materialId, orientation {roll} | {vector}, releases i/j 6 bools, offsets, timoshenko, design {Ky, Kz, Lb, Cb, bracedLateral}, behaviour both (tension/compression-only reserved), role primary|secondary override, starter flags locked|hidden|required}, shells[], regions[], links[], constraints[] (present, validated, engine rejects at MVP with ENG-UNSUPPORTED-KIND), supports[] {nodeId, dof 6 x fixed|free|{k}, localAxes}, loadCases[] {type dead|superDead|live|roofLive|snow|wind|seismic|temperature|settlement|other, selfWeight, generator {kind, params, provenance}}, loads[] (nodal, memberDistributed, memberPoint, thermal, areaPanel, settlement; generated loads carry provenance scenario), panels[] one-way at MVP, combinations[] {type strength|service|seismic, code ref, terms, envelope}, analyses[] {kind linearStatic (modal|buckling|pDelta reserved), params}, groups[], meta (non-semantic: labels, authorship). Every element has a client-generated, never-reused typed id; cross-references are by id; ordered collections carry fractional order keys; deletions tombstone in the op log, not the model. Hashes: model_hash, result_hash (embedding engine_ref and numeric_profile), scenario_hash, evidence_hash, submission_hash, grade_hash, deliverable hashes. ## Solver and checks core

Language and build: Rust 2021 workspace under crates/ with bridle-canon, bridle-fem, bridle-checks, bridle-packs, bridle-scenario, bridle-fingerprint, bridle-wasm (wasm-bindgen facade) and bridle-cli (native). Two wasm artifacts are produced per release with wasm-pack for wasm32-unknown-unknown with simd128 enabled and no relaxed SIMD, no threads, no FMA, libm crate for transcendentals: engine.wasm (bridle-fem plus bridle-canon; target <= 1.5 MB raw, <= 500 KB gzipped, instantiates in < 300 ms) and checks.wasm (bridle-checks, bridle-packs, bridle-scenario, bridle-fingerprint plus bridle-canon; same size budget; pack data loaded at runtime so the binary stays small). Each artifact is content-addressed (engine:bridle-fem@0.x.y#sha256:..., checks:bridle-checks@0.x.y#sha256:...) with a manifest carrying wasm_digest, native_digest and numeric_profile (wasm32-simd128-st at MVP; x86_64-native-st and aarch64-native-st for the native build). The native build compiles and runs the same tests in CI from day one; it powers bridle-cli (replay, benchmark, harness, pack publish) and is the Tier-3 server path in v1.x. Determinism: server grading runs the identical wasm bytes in Node worker_threads (V8 wasm is deterministic for the non-relaxed subset), so R7's bit-identical claim holds trivially within an artifact; sorted entity ids drive assembly order, BTreeMap or sorted Vec only, single-threaded kernel, fixed start vectors for future eigen solves, no clocks or randomness; CI asserts identical result_hash on the benchmark suite across Node wasm, Chromium, Firefox, WebKit and native Linux and macOS (native versus wasm compared by tolerance 1e-9 and recorded as result_match). Engine design: element registry keyed by kind string with trait Element (frame12 with static condensation for releases and transformation for rigid offsets and Timoshenko shear areas; truss with automatic rotational DOF elimination; nodal spring and zero-length link); analysis registry with trait Analysis (linear_static multi-case multi-RHS with prescribed displacements; slots for modal, buckling, p_delta sharing K_G code); AMD ordering plus simplicial LDLT (faer-sparse evaluated in the week-1 spike against the acceptance of a 10-storey 6x6-bay frame of about 3.2k DOF in < 50 ms; fallback is an in-house CSparse-style LDLT of about 2k lines), dense symmetric path below 500 DOF, one step of iterative refinement, residual recorded; incremental re-solve reuses the factorization for load-only edits and the symbolic ordering for geometry edits; combinations and envelopes by superposition; validation rules VAL-* (< 20 ms on S models) and ENG-SINGULAR with node and DOF localization and a null-space mode for animation; stations default 11 with analytic extrema and values at load discontinuities. Checks design: trait LoadsPack and trait ResistancePack (details in code_packs), limit-state catalog (T-YIELD, T-RUPTURE, C-FB, C-FTB, F-YIELD, F-LTB, F-FLB, V, H1, SLEND-C, SLEND-T, DEFL, DRIFT, CLASS), stability from first-order results (B1/B2 amplification per AISC Appendix 8, notional loads as cases, ASCE 7-22 12.8.7 theta, mechanism detection, ELM validity Delta2nd/Delta1st <= 1.5), QUAL-01 efficiency, QUAL-02 economy against the seeded benchmark, QUAL-03 connectivity and both-direction LFRS gates, ERR-01..07 detectors (ERR-06 compares declared Lb/K against author bracing only; ERR-08 steel material pairing rules), SITE-06 consistency rules as data (>= 15 rules), deliverable comparators (three-way answer classification with unit fingerprints 1000, 12, 25.4, 47.88, 4.448; findings versus check key with the 0.50/0.15/0.15/0.10/0.10 credit split and unsafe-approval gate; Diagnose detection and correction predicates), every outcome emitted as a GradeEvidence v1.0 record with clause ids validated against the clause library. Verification: about 25 closed-form benchmarks for MVP analysis types (cantilever, SS and fixed-fixed beams, propped cantilever, settlement, thermal bar, portal sway, Warren truss, beam on springs, releases, offsets, partial loads, projected loads, 2D mode parity) with tolerance 1e-6 relative for exact elements; AISC Design Examples v16.0 reproduced within 2% for >= 30 examples with SME-authored inputs; 5-10 OpenSees cross-checks offline (never shipped); performance scenes for S and M tiers with a 15% regression gate; the fast subset runs on every PR in <= 3 minutes. Model-size tiers: S (<= 200 members, about 1.2k DOF, solve plus render <= 100 ms p95) and M (<= 2,000 members, about 12k DOF, <= 300 ms p95) on the reference laptop (4-core 2020 laptop, integrated GPU, 8 GB); authors set a per-task hard cap (members and DOF) that the workspace, the submit API and the analysis worker enforce identically; estimate() exists at MVP to switch live mode to manual Run mode above budget (no device calibration, no L tier); server standard sandbox 2 vCPU / 2 GB / 60 s; artifact retention >= 3 years; task re-pin is explicit with a diff report.

## Live loop

Path: a UI gesture produces one or more ops through the command bus (toolbar, shortcut, palette and tests share it); the zustand store applies them to the immutable document (< 1 ms) and appends them to the local op buffer (IndexedDB autosave <= 2 s, server segment flush every 5 s or 500 ops); the EngineClient posts applyOps(ops, seq) to the engine worker, which updates its internal model and returns validation issues (< 20 ms for S); a debounced solve (30 ms after the last edit, at most every 100 ms during a drag) runs linear static for all cases with factor reuse (load-only edits < 10 ms, geometry edits reuse the symbolic ordering), then runChecks with the pinned pack bundles for utilization and the live findings the assistance profile allows; results return as Float64Array transferables plus a JSON index; the scene builder updates only dirty buffers (<= 16 ms) and the overlays (deformed shape, N/V/M diagrams, reactions, utilization color map, equilibrium panel) repaint; combination switching repaints from cached case results without re-solving. Latency budget per edit on the reference laptop: op apply 1 ms, applyOps and validate 20 ms, solve S 50 ms p50 (M 200 ms p50), checks 20 ms, transfer 2 ms, scene update 16 ms, giving S <= 100 ms p95 and M <= 300 ms p95 commit-to-fresh-results (R14); the main thread never blocks more than 16 ms because all numerics run in the worker. Staleness and ordering: every solve carries a monotonically increasing seq; the worker skips superseded requests and cancels within 200 ms; the UI drops stale responses and marks overlays stale (desaturated plus badge) within one frame of an edit; dropping 100 edits in one second yields at most about 30 solves and the last result always matches the final model. Self-check: the same checks.wasm and pack bundles run locally for the pre-submission self-check with the archetype-specific disclosure level; because the artifacts match the pinned server artifacts the self-check evidence equals the server deterministic evidence by hash. Fallback to server: estimate() predicts factorization cost from the symbolic analysis; if predicted time exceeds the tier budget, the model exceeds the author cap, or the user forces it, the workspace switches to manual Run mode and POSTs an analysis job in the interactive lane (p95 queue wait <= 5 s, 60 s wall clock); progress and completion arrive over the WebSocket stream and the result document has the same schema, so overlays do not care where the solve ran. Resilience: the worker is restarted automatically on crash preserving the last good results; a 1 GB wasm memory cap and a 5 s live-tier solve budget cancel runaway solves with an explanation; API or LLM outages do not affect editing or live analysis (local autosave queues ops for reconnect with last-writer-wins per object plus a restore-previous option). Exam mode: the server does not issue the checks.wasm URL or pack bundles to exam sessions, so live utilization is impossible rather than hidden; analysis results visibility (full, analysis-only, none) is enforced by the client build hash recorded in the attestation.

## Code packs

A code pack is an immutable, content-addressed artifact that combines data and a small amount of pure Rust. Structure (packs/<pack-id>/): manifest.json {ref codepack:us-asce7-22@1.0.0#sha256, edition, jurisdiction, traits [loads|resistance], native_units, display_vocabulary, legal_basis, attribution, licensing_register_ids, verification_record_ref, supersedes}, tables/*.json (coefficient tables in Bridle's own schema keyed by clause id with units and provenance, limited to the curriculum subset; derivable tables computed at runtime), combinations.json (named sets LRFD 2.3.1 plus 2.3.6, ASD 2.4.1 plus seismic, service sets, direction and sign expansion rules), consistency-rules.json (SITE-06 rules: id, condition DSL, message_key, severity), limit-states.json (ids mapped to clause library keys and section families), serviceability-presets.json, systems.json (reduced Table 12.2-1 subset with Bridle labels), clauses/ (clause library: id, paraphrased title, Bridle explanation, typical fixes, official link; no verbatim text), na/ (national-annex overlays, empty for US), conformance/ (fixture scenarios, SME-authored benchmark inputs and expected values with tolerances), verification-record.json plus .sig, CHANGELOG.md with errata severities. Code side: crates/bridle-packs defines trait LoadsPack { id, derive_actions(scenario_instance, model, options) -> ActionSet (load cases with generator provenance and intermediate parameters such as Kz, qz, Cs, T, k, pf), generate_combinations(action_set, method) -> CombinationSet, service_combinations(...), consistency_rules() } and trait ResistancePack { id, applicable(member, section_family, material) -> bool, classify(section, material) -> Classification, check(member_context, demands_per_combination, design_attrs) -> Vec<Verification {limit_state, demand, capacity, ratio, governing combination and station, clause_id, values map, status}> }; a pack crate implements one or both traits over its bundle data; packs/registry.json lists every pack with traits, editions, units vocabulary, verification status and the licensing register entries. The stage model is fixed: actions -> combinations -> effects (engine) -> resistances -> verifications -> findings (GradeEvidence), so a pack never touches the engine, the grader or the UI. Loading: the browser and the analysis worker fetch bundles by digest (lazy, cached immutable); Packs::load returns a PackHandle; a task pins code_pack_refs[] (typically one loads pack and one or more resistance packs) through its activity pin set; packs in state revoked are refused except in replay mode. Versioning: semver where MAJOR is a code-edition change (ACI 318-19 to 318-25, first- to second-generation Eurocode), MINOR adds checks or coverage, PATCH is errata; publish requires an approved licensing register entry, a passing conformance suite, the no-verbatim similarity gate (or two-reviewer attestation where the publisher forbids automated scans), a signed SME verification record bound to the bundle hash and the two-person promotion rule; published versions are immutable and remain runnable for 3 years; a changed pack never alters grades of published tasks because tasks pin refs. Clause traceability: every Verification and every GradeEvidence record carries code_ref {pack ref, clause id, library id}; the grounding validator rejects clause ids absent from the pinned clause library; help pages for checks and clauses are generated from the same catalogs; the learner-facing 'show my loads' panel lists each derived load with its scenario parameters and clause. How the second pack plugs in: add crates/packs/ph-nscp-2015 (LoadsPack with Section 203 combinations, 205 live loads, 207 wind, 208 UBC-97-lineage seismic with zones, soil profiles, Na/Nv; ResistancePack delegating to the AISC 360 and ACI 318 modules parameterized by NSCP factors) or crates/packs/eu-en1990-1993-gen1 (LoadsPack with EN 1990 6.10/6.10a/b and SLS combinations driven by psi factors from na/uk.json; ResistancePack for EN 1993-1-1 classes, 6.2 resistances and 6.3 buckling curves), its data bundle, >= 20 published worked examples in conformance/, an SME verification record, licensing determinations (LIC-08) and a registry entry; the task builder's code-basis picker, units vocabulary (I18N-02) and the starter templates read the registry, so no UI or grader code changes. The MVP proves the seam with packs/conformance/fixture-partial-factor, a tiny non-US fixture pack exercising psi-factor combinations and a different unit vocabulary through the same traits, and with the EN 1990 combination generator kept as a conformance test only. Reference libraries (sections, materials, cost index, named sites, seeded-error catalog) follow the same artifact and registry rules.

## Grading pipeline

Stages (each a BullMQ job with a content-addressed, persisted output; re-runs resume from the failed stage): S0 intake (API transaction at submit): validate the submission against the deliverable schemas and the archetype, recompute model_hash with bridle-canon and return 422 on mismatch, apply size and rate limits, resolve the learner's scenario instance and activity pin set, compute deliverable hashes, fingerprint and EditCadenceSummary, scrub PII from the memo (names, emails, ids, institution) with the scrub log, store the submission pin set and receipt (submission_hash), create grading_job with idempotency key (submission_id, pinset_id, grader_ref), emit bridle.lms.submission.submitted. S1 analysis (lane grading): analysis-worker runs the pinned engine artifact on the stored revision with loads and combinations derived from the instance by the pinned loads pack; stores result_set by result_hash; result_match in {exact, within_tolerance, mismatch, not_compared}; a mismatch produces a model_integrity evidence record and a review flag, never a learner penalty. S2 rules: checks.wasm in a worker_thread runs validity and stability, scenario consistency, load and combination diff, member checks under all required combinations, serviceability and drift, stability advisories, task constraints, efficiency and economy versus the seeded benchmark, archetype deliverable grading (answers, findings, found errors, memo bounds, required snapshots verified from sidecars), instance-binding verification and reference match; output EvidenceSet (GradeEvidence v1.0 records: evidence_id EV-<type>-NNNN stable per snapshot and grader, criterion_ids, check_type, subject, status, severity, metric with unit and limit and margin, governing combination, values map, code_ref, message_key, visual payload, computed_by) with evidence_hash, plus the deterministic EvidenceDigest (all fail and warn up to a cap, top-N governing per check type, all constraint, integrity, analysis_error and efficiency records, summary stats, sorted keys, no timestamps or identity; size checked with count_tokens against the 12k budget). S3 judge (skipped for deterministic-only tasks, kill switch or budget breach, leaving judged criteria pending): screen call on claude-haiku-5-5 (injection, PII residue, off-topic, language; non-allowed language routes to review); judge call on claude-opus-5-5 with thinking adaptive and effort pinned per route (summative high, formative medium; tuned by the harness) returning JudgeResult via output_config.format (criteria[] with level enum 0-3, evidence_refs required, memo_claims with verdict supported|unsupported|contradicted, confidence enum, flags enum; no field can touch auto scores); narrative call returning FeedbackNarrative (summary, strengths, issues each with evidence_id, clause_library_id, action, priority, next_steps); grounding validator (every evidence_ref exists; every numeric literal matches the digest or the allow-list after unit and precision normalization; every clause id exists in the pinned clause library; contradicted verdicts carry refs) with one regeneration through a role system correction message and template fallback plus validator_fallback flag on a second violation; Check and Diagnose judged reasons limited to 40 failing entries in one call. Prompt layout: system block 1 (grader charter, untrusted-data framing, schema semantics; cache_control 1-hour TTL, > 512 tokens), system block 2 (task block: judged criteria with level descriptors, clause explanations present in the task, scenario summary, author guidance; 5-minute TTL, 1-hour around deadline windows), user turn (digest JSON with sorted keys, memo inside explicit untrusted delimiters, instruction); temperature and top_p never sent; max_tokens 8k; cache_read_input_tokens asserted > 0 on the second grade of a task in an integration test; alert when cache read share drops below 30% for an hour. Judge cache: judge_invocation keyed by hash(prompt bytes, model id, effort, schema ref) returns stored output on identical input; prompts and responses stored encrypted with 12-month retention; request_hash, response_id, response_model, usage and inference_geo recorded on the grade pin set. S4 aggregate (pure TypeScript function, recomputed from stored rows on display): scoring functions (step, banded_max_metric with utilization <= 1.00 pass, 1.00-1.02 advisory, above Critical or Major per GRD-03, fraction_scaled within the passing region, linear_margin, level_map {0:0, 1:40, 2:75, 3:100}), weights from the rubric version with the archetype activation matrix, gates in order fail-task then caps (Critical cap 50, Major strength or loads cap 75, unsafe approval cap 75, optimization feasibility gate), rounding, confidence (0.35 judge confidence, 0.20 evidence completeness, 0.15 validator retries, 0.15 distance from threshold, 0.15 memo signal), flags (confidence < 0.7, within 3 points of pass mark, any critical gate, injection or contradiction or possible_copy, refusal, validator fallback, result mismatch, integrity high). S5 review: queue projection ordered by flag severity, confidence and age, section-scoped; side-by-side viewer with evidence highlighting at the governing combination; archetype comparison tables; per-criterion and entry-level adjudication with mandatory reason creating grade version n+1 (regrade_reason instructor_override, judge criteria carried); summative release by instructor or TA action (100% review at MVP), formative deterministic results released immediately with the narrative labeled AI-provisional; release emits grade.released for gradebook, notifications and analytics. Reproducibility and regrades: regrade_reason in {initial, instructor_override, pack_upgrade, engine_upgrade, rubric_fix, grader_release, judge_rerun, appeal, calibration, integrity_review}; re-pinnable fields are engine, numeric profile, result, libraries, rubric version of the same rubric, grader, prompt, judge schema, model id and api version; never re-pinnable are learner, model_hash, scenario_hash, task_version, content_version, justification and attachments; deterministic criteria are always recomputed and judge criteria re-invoked only for judge_rerun, pack_upgrade, rubric_fix, appeal and calibration; bridle-cli replay <grade_id> re-executes the deterministic stages from the pin set and asserts result_hash, evidence_hash and deterministic scores (nightly sample in v1.x). Latency and cost targets: deterministic stage <= 10 s p95 for M models (<= 60 s p95 under PERF-05), judge stage <= 60 s p95, end to end <= 90 s p95, deterministic evidence visible within 15 s regardless of judge status; median cost about $0.13 per grade on the Opus route (12k cached read, 6k fresh input, about 5k output including thinking, plus the Haiku screen), p95 <= $0.40; regrades, calibration and the harness use the Batches API at 50% off; a per-course daily spend cap pauses judge stages while deterministic grading continues; a 500-submission burst yields deterministic checks 100% within 10 minutes and judged feedback 95% within 30 minutes with adaptive LLM concurrency and jittered backoff so no 429 becomes a failed grade. Offline harness: tools/grading-eval runs golden sets (oracle >= 95, null = 0, flawed variants per archetype, memo variants including injection and non-English) with 3 repeats and gates promotion at exact-level agreement >= 85%, within-one-level >= 97%, kappa >= 0.80, flip rate <= 2%, injection pass >= 99%, cost within COST-02.

## Jobs and queues

BullMQ 5 on Redis 7 (one Redis at MVP; sharded later behind the same queue names). Queues and lanes: analysis (priority lanes interactive=1, grading=5, batch=10; concurrency 4 per worker task; per-user cap 2 and per-tenant cap 50 enforced with a Redis semaphore acquired before processing, otherwise the job is delayed-requeued with jitter so no tenant starves another); grading-stages (grading.intake is synchronous in the API transaction; grading.analysis, grading.rules, grading.judge, grading.aggregate as a BullMQ flow with per-stage retries: 3 attempts for infrastructure classes, 0 for deterministic failures, stage wall clocks 60 s deterministic and 5 min judge with a 3x hard ceiling); llm (concurrency limiter tuned to the Anthropic rate limit with adaptive backoff, 429 and 529 never fail a grade, kill switch and budget checked at dequeue); batch (calibration runs, bulk regrades, harness, pin-override regrades; may be delayed up to 60 minutes; uses the Batches API for judged criteria); similarity (at task close and nightly when enabled); outbox-publisher (polls outbox_event every 250 ms, publishes to Redis Streams, consumer groups per projection, idempotent by event id, ordered per source seq); projections (gradebook, progress, mastery, notifications, analytics, audit sink); notifications (email through a transactional provider, in-app inbox); reconciliation (every 15 minutes: every submission has exactly one active or terminal grading job, every terminal job has a grade version, a dead-letter entry or an audited cancellation; violations page and auto-recreate the job preserving the original submit timestamp; lost-work counter); retention (daily per event class and for op segments, prompt logs, diagnostic bundles, draft history); artifact-cache warmers; llm-backfill (oldest-first after a kill switch or budget pause). Dead-letter: BullMQ failed set mirrored into a dead_letter table with a classified reason (solver_error, model_validation_error, llm_error, infrastructure, unknown) and the full replay payload; replay individually or in bulk from the operator console; discard requires a reason. Worker pool at MVP: ECS services worker-analysis (2 tasks, 2 vCPU / 4 GB, each running up to 2 sandboxed worker_threads with a 1 GB wasm memory cap), worker-grading (2 tasks, 1 vCPU / 2 GB, runs rules in worker_threads and the judge stage), worker-system (1 task: outbox, projections, reconciliation, retention, similarity, notifications); fixed pool sized for 300 analyses/min and 1,000 grades/hour; autoscaling on queue age is v1.x. Job payloads carry traceparent for end-to-end tracing and are versioned schemas; every enqueue carries an idempotency key; BullMQ job ids are deterministic from the key so duplicates collapse. Observability: queue depth and oldest-job age per lane, stage durations, failure rate by reason, dead-letter age (> 15 minutes alerts), per-tenant concurrency usage. Event bus seam: EventBus interface with the Redis Streams implementation; NATS or Kafka replaces it for multi-cell fan-out without touching emitters or projections.

## Observability

OpenTelemetry everywhere: the browser propagates traceparent on fetch and WebSocket frames and reports Web Vitals (LCP, INP, CLS) and workspace timings (solve, checks, scene update, fps) as pseudonymous RUM events; the API uses Node auto-instrumentation with the required log fields (trace_id, span_id, tenant_id, opaque actor_id, job_id, task_id, solver_version, model_hash, grader_prompt_version); BullMQ jobs carry traceparent in payloads so a grade is one trace from submit through analysis, rules, judge calls (Anthropic SDK instrumented with model id, effort, tokens, cache reads, latency, stop reason, validator outcome) to release; engine phases (assemble, symbolic, numeric, solve, recovery, checks) are span attributes emitted by the host from wasm timings. Sampling: 100% of jobs, >= 10% of HTTP, all errors. Logs are structured JSON with a CI redaction test proving no emails, names or memo text reach logs; application logs 30 days, audit 7 years in WORM. Metrics (Prometheus via the OTel Collector into Grafana Cloud Mimir): RED per route; queue depth, oldest-job age and wait by lane; job duration by stage and tier; solver failure rate by reason; LLM latency, tokens, cost per grade, cache-read share, refusal and validator fallback rates; result-cache hit rate; WebSocket connections; per-tenant LLM spend and compute seconds; lost-work counter; reconciliation violations; exam-mode refusals. Alerts (multi-window burn rate paging to a hosted pager, MTTA <= 15 minutes business hours): pipeline failure rate > 1%, queue lag > 5 minutes, stuck job beyond stage budget (within 10 minutes), dead-letter entry older than 15 minutes, cache-read share < 30% for one hour, hourly LLM spend > 3x the 7-day average, tenant budget at 80% and 100%, reconciliation violation, RLS or authorization test alert, deadline-window escalation. Cost observability at MVP: component-level cloud cost tags (env, component) with a daily dashboard plus per-tenant LLM counters from response.usage and compute seconds from job timings; per-tenant cloud attribution and anomaly detection are v1.x. ## Answers to open questions

Q1 Launch geography and second pack: launch in the US with the US pack (ASCE 7-22 plus AISC 360-22, ACI 318-19 as v1.1) and US customary plus SI display. Make the second pack NSCP 2015 if the first signed non-US customer is in the Philippines (the founding team's stated market), otherwise first-generation Eurocode (EN 1990/1991/1993 with the UK National Annex overlay); decide at the first non-US contract, not before. Either way the MVP proves the pack seam with the partial-factor conformance fixture and the EN 1990 generator as a conformance test, and the LIC-08 licensing determinations (ASEP permission, CEN/NSB and the EU database right for profile tables) start in the first v1.x planning sprint so the chosen pack is a 6-8 engineer-week increment rather than a legal discovery. Q2 Backend language: TypeScript end to end for every service, with one Rust core for the engine, checks, pack runtime, scenario, fingerprint and canonicalization. Python is not needed in production: the grading service is orchestration over deterministic Rust stages and the Anthropic TypeScript SDK supports structured outputs, Batches and token counting; Python appears only in offline OpenSees cross-check scripts under tools/. This keeps one schema codegen path (Rust to JSON Schema to TS), one deploy toolchain and one on-call skill set. Q3 Hosting: AWS, single region us-east-1 at MVP, all managed (ECS Fargate, RDS Postgres 16 Multi-AZ, ElastiCache Redis, S3 with Object Lock for audit, CloudFront, KMS, Secrets Manager), defined in OpenTofu as a cell module; EU residency later is a second cell (eu-central-1) plus a tenant directory and EU-pinned LLM inference, not a migration. If the team has no AWS operator, a managed-container provider (Render or Fly.io) with managed Postgres and S3-compatible storage is an acceptable interim because every service reads its endpoints from CellContext, but AWS is the recommendation because Object Lock, KMS per-tenant keys, cross-region backups and the EU cell all exist there without a second vendor.

## Trade-offs

Pros:
- One Rust core shipped as the same wasm bytes to the browser and the server makes browser/server parity and reproducible regrades a structural property rather than a tolerance contract, and keeps server compute per analysis near zero.
- Registries and traits (element kinds, analysis kinds, LoadsPack/ResistancePack, IdentityProvider, EventBus, CellContext) mean the known growth items (shells, modal, P-delta, NSCP, Eurocode, SAML, LTI, EU region, NATS) are additive crates, bundles or stack instances with no stored-data migration.
- Content-addressed artifacts and the DM pin set on every submission and grade make 'which grader graded this' answerable in one query, allow pack and engine rollouts mid-term without touching published tasks, and make errata replay deterministic.
- A single schema package and one canonicalization implementation prevent the four-way hash divergence the critic found and give every domain the same ids and events.
- Boring shell technology (Next.js, Fastify, Postgres with RLS, BullMQ, S3, Anthropic SDK) is well understood by a small team and has first-party tooling for OpenAPI, tracing and local development.
- Structured outputs, prompt caching, pinned exact model ids, a grounding validator and a persistent judge cache give a defensible, auditable judge at about $0.13 per grade without relying on sampling parameters the API rejects.
- Data-driven packs with clause-keyed coefficient tables keep the licensing position on the facts-and-methods side and make the no-verbatim and verification gates enforceable in CI.

Cons:
- Rust is a second language for a TypeScript team; the engine, checks and packs are the critical path and the faer-sparse-on-wasm question must be settled in week one.
- Running the judge on Opus for formative tasks costs roughly twice the Sonnet route; switching later is a configuration and calibration exercise but it is still a grader_version change.
- Reserving seams (team fields on documents, lock epochs on every op, region on tenants, shell and analysis slots, pack traits) costs schema and test effort at MVP that only pays off when the features arrive.
- Running the same wasm on the server caps authoritative solves at single-threaded wasm speed; large Tier-3 models wait for the native path in v1.x.
- Postgres RLS adds per-request transaction discipline and some query-planning cost; every new table needs a policy and the CI test is the only thing that catches omissions.
- A single AWS cell with managed services keeps operations simple but puts EU residency behind a second-stack project and ties the stack to one provider.
- Two wasm artifacts plus pack bundles are more moving parts to pin than one blob, in exchange for exam-mode enforceability and independent versioning.

## Risks

| risk | mitigation |
|---|---|
| faer-sparse does not build or perform on wasm32, or the LDLT is too slow for M-tier live budgets. | Week-1 spike with the 3.2k DOF benchmark; fall back to an in-house CSparse-style simplicial LDLT (about 2k lines) behind the same Engine API; M tier can degrade to manual Run mode through estimate() while the live promise holds for S. |
| Small team lacks Rust depth and the core slips, blocking the workspace, checks and grading. | Bound the core scope (frame, truss, spring, linear static), pair Rust work with the benchmark suite from day one, keep the engine protocol language-agnostic so a TypeScript Tier-1 fallback remains possible, and start packs (mostly data plus small pure functions) in parallel once the traits are fixed. |
| Quanta, allowlist or axis conventions frozen in canon/1 turn out wrong, invalidating stored hashes. | STR and FE review the quantum table before the schema v1 freeze, golden vectors encode expected sensitivity, canon bumps are additive with recorded canon_version on every pin set and hashes are never recomputed. |
| AISC Shapes Database license does not cover SaaS use or ACI consent is refused. | Execute the AISC license before enabling the steel pack with the user-upload and derived-properties fallback behind a flag; keep the ACI pack feature-flagged off with a steel-and-loads MVP curriculum; licensing register gate blocks accidental shipping. |
