# Proposal: Lockstep: Bridle MVP architecture (determinism-first)

_Angle: Correctness and determinism first. The browser and the grading worker execute the same WebAssembly bytes; every input and every artifact a grade depends on is content-addressed and pinned; every score is backed by a hashed evidence record; and the only non-deterministic component (the LLM judge) is fenced to judged criteria, grounded in the evidence digest, schema-constrained, validated, cached and stored verbatim with request and output hashes. Verification against published worked examples, a cross-host hash matrix in CI and a nightly replay of released grades turn reproducibility from a claim into a monitored property. The live loop is made as fast as that allows: Tier S 100 ms p95, Tier M 300 ms p95 on the reference laptop, with the budget shown stage by stage._

## Summary

Lockstep is a TypeScript monorepo built around one Rust core, bridle-core, that contains the FE solver, the code-pack runtime and checks library, the scenario and seed engine, deterministic deliverable grading, and the canonicalization and hashing rules, and that ships as exactly one content-addressed WebAssembly artifact. The browser runs that artifact in a Web Worker for the live edit-solve-render loop and the pre-submission self-check; the grading worker runs the identical bytes under Wasmtime with fuel and memory limits, so browser-versus-server parity is a property of the artifact digest rather than a cross-compilation claim, and the R7 resultHash integrity check is bit-exact whenever the digests match. Everything a grade depends on (engine, code pack, clause library, section and material libraries, cost and hazard datasets, rubric version, prompt template, judge schema, model id and effort, grader release) is an immutable ArtifactRef in a registry with per-type gates and a two-person promotion rule, and every submission and grade version stores its full pin set so any grade can be replayed from a bundle. Postgres 16 with row-level security holds tenant state and append-only versioned tables; S3 holds content-addressed model revisions, result sets, evidence, prompt and response logs and artifacts, with an Object Lock bucket for the audit class; Redis backs BullMQ lanes and the outbox-fed event stream. The grading pipeline has six isolated stages (intake, re-analysis, checks and deliverable grading, judge, aggregation, review); stages 0, 1, 2 and 4 are pure functions of the pin set and produce an evidence record whose hash is part of the grade, and the judge stage (claude-opus-5-5 with adaptive thinking and pinned effort, claude-haiku-5-5 pre-screen) sees only the evidence digest and the scrubbed memo, returns schema-constrained output with no field that can touch an auto-scored criterion, passes a grounding validator, and is stored verbatim with request and output hashes. Verification is continuous: a closed-form and worked-example benchmark suite runs on native, Node, Wasmtime and three browser engines asserting identical result hashes, each pack release carries a signed PE/SE verification record bound to the bundle hash, the grader is gated by an offline harness, and a nightly job replays a sample of released grades. The live loop budget is 100 ms p95 for Tier S and 300 ms p95 for Tier M on the reference laptop, shown stage by stage, with a manual same-artifact server run as the only fallback. The second code pack plugs in as data plus a Rust module behind a six-stage Pack trait whose conformance suite already includes EN 1990 and NSCP 203 fixtures. Schema seams for teams, integrity and collaboration (ownership fields, actor-stamped ops, stable element ids, one anchor model, pin sets) are in the MVP schema so no stored document needs migrating later. Infrastructure is deliberately boring: Next.js, Fastify, Postgres, Redis, S3 and ECS Fargate in one AWS region, managed by OpenTofu. The MVP is about 105 engineer-weeks across 16 steps, roughly eight to nine months for a team of five, and it starts with the schema and canon crate because every hash recorded afterwards depends on them.

## Data model

**Tenancy:** Organization-scoped tenancy enforced in the database: tenant_id plus an RLS policy on every tenant-scoped table; the API sets app.tenant_id and app.actor_id with SET LOCAL per transaction from the verified session and the application role cannot bypass RLS (only the migration role can); users are global and attach to tenants via memberships with scoped roles; object keys are tenant-prefixed and served through 15-minute signed URLs; cross-tenant access exists only for platform-admin operations through reason-logged console paths; similarity, calibration and analytics never cross tenants; tenant.region is stored and fixed to 'us' at MVP; the free sandbox is itself a tenant with a deterministic-only plan.

**Storage:** Postgres 16 (RDS Multi-AZ, PITR) for all relational state, with JSONB pin columns and generated indexed columns, immutable tables protected by REVOKE UPDATE/DELETE and triggers, monthly partitions for events and op segments; S3 for every blob keyed by content hash under a tenant prefix (model revisions, result sets, evidence, prompt and response logs under a separate KMS key, op-log segments, attachments, snapshots, exports) and by digest for artifacts, with an Object Lock compliance bucket for the audit archive and cross-region replicas; Redis for queues, streams, limits and caches only; IndexedDB in the browser for autosave and unsent ops.

## Structural model schema

Package and source of truth: packages/schema is the single contracts package; the Rust structs in crates/bridle-canon/src/model/ annotated with schemars generate bridle-model.schema.json (JSON Schema 2020-12), TypeScript types and zod validators; CI fails if the committed JSON differs from the generated one, and a lint blocks any JSON.stringify or serde_json based hashing outside bridle-canon. Versions: bridle-schema@1.0.0 (semver; minor versions are additive and readable by N-1 consumers for 90 days), canon:1 (any change to the semantic allowlist, quanta, ordering or header bumps canon and never rewrites stored hashes), bridle-events@1.0.0. Document shape (semantic model only): header {schema:'bridle-model@1.0.0', kind:'model'}; settings {mode:'3d'|'2d-xz', analysis:{timoshenko:bool, stations:11}}; materials[{id, type:'isotropic', E, nu, rho, alpha, design{grade, fy, fu | fc}, source_ref}]; sections[{id, kind:'catalog'|'parametric'|'custom', catalog{lib_ref, label} | params{...}, props{A, Iy, Iz, J, Cw, Sy, Sz, Zy, Zz, ry, rz, Asy, Asz, bf, tf, tw, h}}]; nodes[{id, x, y, z, level_id?}]; levels[{id, elevation}]; members[{id, type:'frame'|'truss', node_i, node_j, section_id, material_id, roll_angle, releases{i, j: 6 bool}, offsets{i, j}, design{Ky, Kz, Lb, Cb, braced_top_flange, role:'primary'|'secondary'|null}}]; links[{id, node_i, node_j, stiffness6}]; supports[{id, node_id, dof6: 'fixed'|'free'|{k}, local_axes?}]; load_cases[{id, type: D|SD|L|Lr|S|W|E|T|settlement|other, self_weight?{factor, dir}, generator_provenance?}]; loads[{id, case_id, kind: nodal|member_distributed|member_point|thermal|area_panel|settlement, target_id, axes, projected, values}]; panels[{id, polygon[node ids], distribution:'one_way', span_dir}]; combinations[{id, type: strength|service|seismic, code_ref, terms[{case_id|combo_id, factor}], envelope}]; groups[{id, member_ids}]; analyses[{id, type:'linear_static', params}]. Reserved (schema-present, validation-rejected at MVP so v1.x needs no migration): shells, regions, constraints (diaphragm, rigid link), behaviour tension-only/compression-only, modal, buckling and p_delta analyses, two_way panels. Non-semantic data lives outside the model: view state (camera, visibility, named views, probes, display units, grid definitions) in a separate view document; ownership and lifecycle fields (owner_type, owner_id, team_id, course_id, section_id, task_id, created_by, forked_from, schema_version, head_seq) on the model_document row (GAP6-01); comments in the collaboration layer keyed by element id (GAP6-04); derived results never in the model or op log. Ids: client-generated, typed-prefix ULID/UUIDv7 strings (n_, m_, s_, mat_, sup_, lc_, ld_, pn_, cb_, grp_), immutable and never reused; tombstones live in the op log, not in the model; ordered collections carry fractional order keys; all cross-references are by id, never by index. Conventions frozen in v1 (GAP1-DM-09): right-handed global frame, +Z up, gravity [0, 0, -9.80665]; 2D models in the XZ plane with y = 0 and out-of-plane DOFs implicitly restrained; SI base units only (m, N, N*m, Pa, kg/m^3, K, s, rad), display units never persisted; member local 1 from node_i to node_j, local 2 in the vertical plane toward +Z (vertical members use +X), roll_angle about local 1; major-axis bending is M3; internal-force sign conventions are defined once in bridle-fem documentation. Canonicalization canon/1 (one implementation in bridle-canon, called from the browser worker, from the API via canon-node and from the runner): (1) project the revision onto schema-flagged semantic fields, dropping labels, colours, camera, display props, timestamps, authorship and display units; (2) materialize schema defaults; (3) quantize every number to an integer count of its dimension's quantum with round-half-to-even, -0 to 0, non-finite is an error (length/thickness/offset 1e-6 m, angle 1e-6 rad, force 1e-3 N, moment 1e-3 N*m, line load 1e-3 N/m, pressure/stress/modulus 1 Pa, area 1e-10 m^2, I and J 1e-14 m^4, section modulus 1e-12 m^3, density 1e-3 kg/m^3, temperature 1e-3 K, translational spring 1e-3 N/m, rotational spring 1e-3 N*m/rad, mass 1e-6 kg, acceleration 1e-6 m/s^2, dimensionless 1e-6, currency 1e-4); (4) NFC-normalize strings, lowercase snake_case enums, omit absent optionals (never null); (5) emit collections as arrays sorted by id in JCS string order; (6) prefix the header {"schema":"bridle-schema@1.0.0","canon":1,"kind":"model"}; (7) RFC 8785 JCS bytes -> UTF-8 -> SHA-256 -> 'sha256:<hex>'. Canonical bytes contain only integers, strings, booleans, arrays and objects: no floats, nulls, NaN or Infinity ever. The same rule applies to the other canonical kinds: result (quanta displacement 1e-9 m, rotation 1e-9 rad, force 1e-3 N, moment 1e-3 N*m, stress 1 Pa, utilization 1e-6; rows sorted by (combination_id, entity_id, station); embeds model_hash, scenario_hash, engine_ref, numeric_profile, analysis_options_hash), scenario (header plus scenario_schema_hash, generator_ref, seed and quantized input params only; derived loads are recomputed, never stored in the canonical form), evidence (pins plus GradeEvidence records sorted by evidence_id and quantized as results), deliverables (answers, findings, found_errors, memo, attachments per the GAP3 deliverables schema; SI values at the model quanta, entries sorted by id, no UI state), submission and grade. Hash vocabulary recorded on rows and in pins: model_hash, scenario_hash, result_hash, evidence_hash, digest_hash, deliverable_hashes{answers, findings, found_errors, memo, attachments[]}, justification_hash (NFC UTF-8), oplog_head_hash (segment hash chain), submission_hash, grade_hash, task_hash, rubric_hash, content_hash, pinset_hash, request_hash and output_hash for judge calls. Golden corpus: packages/schema/golden/ holds at least 50 vectors (input -> canonical bytes -> hash) covering relabel, reorder and display-unit invariance and 1 um and 1 mN sensitivity; CI runs it in Rust native, Node wasm and Playwright Chromium, Firefox and WebKit and fails on any byte difference; performance target 5,000 nodes and 10,000 members canonicalized and hashed in at most 200 ms in wasm and 50 ms native.

## Live loop

Path (entirely on the client): a UI command from the toolbar, palette, table editor or gizmo -> the command bus emits invertible ops with a gestureId -> the document store appends to the local op log and autosaves to IndexedDB within 2 s (server op segment every 5 s or 500 ops) -> workspace-worker.applyOps(ops, seq) -> bridle-core validate (VAL-* rules, under 20 ms for Tier M) -> estimate() tier and cap check -> solve(seq) for all load cases by multi-RHS, with factorization reuse for load-only edits and symbolic reuse for geometry-only edits -> check(pack) for AISC utilizations, deflection and drift ratios and the combination envelope -> a result frame of transferable Float64Arrays plus a JSON index keyed by entity id -> the scene builder marks dirty entities and rebuilds only their instanced buffers -> the next animation frame renders the deformed shape, diagrams, reactions and utilization colours. Budget on the reference laptop (4-core 2020 laptop, Iris Xe or M1, 8 GB): Tier S: debounce 30 ms (excluded from the budget), op transfer 1 ms, validate 5 ms, solve 20 ms p50 / 60 ms p95, checks 8 ms, result transfer 2 ms, scene update 8 ms, one 16.7 ms frame; commit-to-pixels 60 ms p50 / 100 ms p95. Tier M: validate 15 ms, solve 120 / 220 ms, checks 40 ms, transfer 10 ms, scene update 20 ms (instanced, dirty-tracked), frame 16.7 ms; 220 ms p50 / 300 ms p95. Drag interactions re-solve at most every 100 ms with the last valid overlay dimmed and badged stale within one frame; superseded solves are cancelled by sequence number so the final frame always matches the final model, and 100 edits in one second yield at most about 30 solves. The main thread never blocks more than 16 ms on engine work (Long Tasks checked in e2e); case and combination switching repaints from cached results in under 100 ms; selection hover resolves under 8 ms with BVH picking. Self-check (PER-02, GAP3-DLV-16) runs selfCheck(profile) in the worker with the very engine and pack artifacts the activity pins, producing GradeEvidence records whose evidence_hash equals the server's deterministic evidence when artifacts match (asserted for every template in CI); disclosure levels 0 to 4 filter what is shown; the self-check payload never contains reference values, check keys or injected error sets; author caps are enforced by a server-side counter endpoint. Artifact delivery: the worker loads /a/{digest}.wasm (immutable cache headers, SRI) and the pack bundle by digest, both taken from the activity pin set, so a learner always runs what the grader will run; exam-mode tasks withhold the pack and checks delivery server-side and the worker runs in analysis-only mode. Fallback to the server: there is no device-calibrated tier router at MVP. If WebAssembly SIMD or WebGL2 is unavailable, the worker crashes twice, or a solve exceeds the 5 s live budget, the workspace switches to manual run mode and offers Run on server, which enqueues an analysis-lane job that executes the identical artifact in bridle-runner (queue wait p95 at most 10 s, run under 1 s for Tier M) and returns the same result frame format; the tabular parity path remains fully usable without the canvas. Grading never depends on client results: the submission carries client_engine_ref, client_numeric_profile and client_result_hash for the integrity comparison only (result_match is exact when the digests match, within_tolerance at 1e-6 relative or one quantum otherwise, and mismatch raises a platform_fault signal that routes to review as a system error, never as a learner error).

## Code packs

A code pack is an immutable data bundle plus a Rust pack module behind one trait; packs never touch the FE engine or the grader. Pack trait (bridle-packs::Pack) with six stages: actions(scenario_instance, model) -> derived load cases with per-value provenance (D from self-weight and SDL, L with reduction, Lr, S flat and sloped, W per direction and GCpi sign, E per direction with Ev and rho, T); combinations(cases, method LRFD|ASD) -> the complete enumerated set with ids and factors including service sets; effects(result_set, combinations) -> per-member and per-station demands and envelopes by engine superposition, never a re-solve; resistances(member, section, material, design attributes) -> capacities with clause ids and substituted values; verifications(demands, resistances, limits) -> per (member, limit state) verdict, demand, capacity, ratio, governing combination, station and clause; findings(consistency rules, learner diffs) -> GradeEvidence records (ERR-03 combination diff, ERR-05 self-weight omission, SITE-06 scenario consistency). Bundle layout packs/<pack-id>/: manifest.json {id, edition, semver, content_hash, licensing_register_ids[], attribution, legal_basis, native_units, check_impl_ids[], clause_library_ref, hazard_dataset_ref}; tables/*.json coefficient tables keyed by clause id with units and edition (ASCE 7-22 Tables 1.5-2, 4.3-1, 4.7-1, 7.3-1 and 7.3-2, 11.4-1 and 11.4-2, 11.6-1 and 11.6-2, the reduced steel subset of 12.2-1, 12.8-1 and 12.8-2, 12.12-1, 26.6-1, 26.10-1; AISC Table B4.1a and B4.1b; tables derivable from equations such as Kz are computed at runtime per GAP2-LIC-02); combinations.json (LRFD 2.3.1 and 2.3.6, ASD 2.4.1 and seismic, service sets); limits.json (deflection and drift defaults); consistency-rules.json (at least 15 SITE-06 rules with id, condition, message, severity); check-catalog.json (check ids, parameters, severities, message templates with placeholders); clause-library.json (clause id, short paraphrased title, Bridle-authored explanation, typical fixes, official link; zero verbatim text; about 50 clauses at MVP); verification-record.json plus detached .sig (PE or SE reviewer, benchmarks per check id, content_hash, not-a-seal statement); CHANGELOG.md (errata with S1, S2, S3). Reference datasets are separate artifacts with their own licensing register entries: sections:aisc-shapes-v16@1.0.0 (served from the backend only under the executed AISC developer license, never bulk-downloadable, with a user-upload and runtime-computed-properties fallback behind a flag), materials:astm-base@1.0.0, hazard:us-sites@1.0.0 (USGS seismic values public domain with credit; wind and snow entered manually for a small named-site set with per-value provenance; no code path fetches the ASCE Hazard Tool), cost:edu-usd@1.0.0 (Bridle-authored educational index from public sources, labelled illustrative). Loading: the worker and the runner call load_pack(bytes, expected_digest); the core verifies the digest, validates the bundle against pack.schema.json, checks that every check_impl_id exists in this engine build and refuses otherwise; packs are cached by digest in the browser (Cache API) and on workers (local disk). Versioning: codepack:us-asce7-22-aisc360-22@MAJOR.MINOR.PATCH#sha256 with MAJOR for a code edition change (ACI 318-25, ASCE 7-28), MINOR for new checks or coverage, PATCH for errata; publishing an existing name and version with a different digest is rejected; tasks pin the pack ref in the activity pin set; changing the pack for a published task requires a pins-only task version and the VP-03 in-flight choice; a pack release requires an approved licensing register entry, the no-verbatim gate (automated 8-word contiguous and 10 percent 5-gram scan where the publisher permits, two-reviewer attestation where it does not), the conformance suite and a signed verification record, and unverified check ids cannot contribute to released grades without an instructor override shown on the report. Clause traceability: every verification and finding carries {pack_ref, clause_id, equation_id, substituted_values{name: {value, unit}}, demand, capacity, ratio, governing_combination_id, station}; the clause id must resolve in the pinned clause library (CI iterates the catalog); the LLM may only cite clause ids present in the digest, enforced by the grounding validator; help pages and the Check limit-state picker are generated from the same catalog, so the workspace, grader and docs cannot drift. How the second pack plugs in: a new crate module implementing Pack plus its data bundle; for NSCP 2015: Section 203 combinations with f1, Section 205 live loads in kPa, Section 207 wind on the ASCE 7-10-style directional procedure with zone-based speeds, Section 208 UBC-97 seismic with Z, Na/Nv, Ca/Cv, R per Table 208-11, T = Ct hn^(3/4), the 2.5 Ca I W / R cap and 0.11 Ca I W floor, and member checks reusing the AISC 360-derived implementations with NSCP Chapter 5 tables in SI; for Eurocode: EN 1990 6.10 and 6.10a/b with psi tables and a National Annex overlay, EN 1991 actions, EN 1993-1-1 classification, 6.2 resistances and 6.3 buckling curves. ## Grading pipeline

Stages, each persisted independently, idempotent per (submission_id, pinset_id, grader_ref), with failures isolated. S0 intake [deterministic; API then worker]: validate the submission bundle against the schemas; recompute model_hash with canon-node from the stored revision and reject with 422 on client mismatch; validate deliverables and completeness rules with the shared validators; freeze the submission pin set (content pins, work pins, client context, provenance, pledge, exam attestation, assistance profile id); scrub PII from the memo with a rule-based scrubber and store the scrub log; verify locked fields are unchanged (CAT-04) and the instance binding (GAP5-RAND-01); emit bridle.lms.submission.submitted; acknowledge with the receipt within 2 s. S1 re-analysis [deterministic]: bridle-runner executes the pinned engine digest with the pinned pack: regenerate the scenario instance from its seed and assert scenario_hash, derive actions and combinations through the pack, solve all cases by multi-RHS, canonicalize and hash the result set; cached by (model_hash, scenario_hash, engine_ref, numeric_profile, analysis_options_hash) for 30 days or while referenced; mechanism or singular results become analysis_error evidence of severity critical so the job completes and gates apply; result_match is computed against client_result_hash. S2 rules and deliverables [deterministic]: pack verifications and findings; task constraints (CHK-03); learner combination and load diffs; support realism and plausibility detectors (ERR-01 to ERR-07 subset); utilization efficiency and economy versus the stored benchmark; archetype deliverable grading in bridle-grade-det (Analyze three-way comparison with unit fingerprints 1000, 12, 25.4, 47.88, 4.448 and 9.80665; Check key matching with 0.50/0.15/0.15/0.10/0.10 entry credit, false-positive, miss and unsafe-approval penalties; Diagnose detection, correction and collateral with the documented constants); memo-model coherence check; everything emitted as GradeEvidence v1 {evidence_id 'EV-<check>-NNNN' stable per (snapshot, grader_version), schema_version, criterion_ids[], check_type (strength | serviceability | stability | load_combination | scenario_load | task_constraint | constructability | efficiency | model_integrity | analysis_error | analysis_accuracy | code_check_reporting | diagnosis | memo_claim), subject{kind, id, label?}, status (pass | warn | fail | not_applicable | error), severity (info | minor | major | critical), metric{name, value, unit, limit, comparator, margin_pct}, governing?{combination_id, combination_label, station, component}, values{name: {value, unit}}, code_ref?{pack_ref, clause, equation, title, library_id}, message_key, visual?{highlight_ids, color_scale, show, combination_id}, computed_by{stage, component_version}}; the evidence set is canonicalized and hashed (evidence_hash) and the EvidenceDigest is built by deterministic selection (all fail and warn records up to a cap, top-N governing per check type, all task_constraint, model_integrity, analysis_error and efficiency records, summaries by check type; sorted keys, no timestamps, no identity) with digest_hash and a count_tokens-verified size of at most 12k tokens; deterministic evidence is visible to the learner within 15 s. S3 judge [non-deterministic, pinned, cached, fenced]: skipped entirely for deterministic-only tasks and the free sandbox; otherwise (a) a screen call on claude-haiku-5-5 with structured output (injection, PII residue, off-topic, language) whose flags route to the integrity queue; (b) one judge call on claude-opus-5-5 covering all judged and hybrid criteria (memo sub-criteria by section id, constructability hybrid, up to 40 failing Check entries) with thinking {type:'adaptive'}, output_config {effort:'high' (pinned per route and always set explicitly because Opus 5.5 defaults to medium), format: the JudgeResult JSON schema with additionalProperties false on every object, enum levels '0' to '3', enum confidence, required evidence_refs}, max_tokens 8,000, via client.messages.parse; no temperature, top_p or top_k (rejected on current models), no tools, no prefill, server-side fallbacks disabled on score-bearing calls so response.model must equal the pinned id (a mismatch is a system error, not a grade); (c) a narrative call producing FeedbackNarrative (summary, strengths with evidence_refs, issues with evidence_id, clause, action and priority, next steps) in the course register and unit system, which never sees reference geometry or sizes; (d) the grounding validator: every evidence_ref exists in the digest and each judged criterion has at least one, every numeric literal matches a digest value after unit and 3-significant-figure normalization or the allow-list (levels, weights, counts, scenario values), every clause id exists in the pinned clause library and the digest, every contradicted verdict carries refs; one regeneration via a mid-conversation role:system message listing the violations (cache-preserving), then template feedback rendered from message_key plus a validator_fallback flag. Prompt layout for cache stability: system block 1 (grader charter, grounding rules, untrusted-data framing, schema semantics; cache_control ephemeral with the 1-hour TTL inside deadline windows) -> system block 2 (task block: rubric level descriptors, clause explanations present in this task, scenario summary; cached) -> user turn (evidence digest JSON with sorted keys, then the scrubbed memo inside explicit untrusted-data delimiters, then the instruction); the prefix is byte-stable (no timestamps or ids), one model and one effort per route, cache_read_input_tokens asserted greater than zero on the second grade of a task in integration tests and alerted when the read share drops below 30 percent for an hour; the minimum cacheable prefix is validated per model from usage fields. Every call stores a judge_invocation row: prompt_ref, judge_schema_ref, llm_model_id, api_version (the anthropic-version header), effort, thinking_type, request_hash (JCS SHA-256 of the full request body excluding auth), response_id, response_model, stop_reason (a refusal with stop_details.category routes judged criteria to needs_review, never to 0), output_hash, usage {input, output, cache_read, cache_write}, inference_geo, validator outcome and retry count; the raw prompt and response are stored encrypted in the llm-logs bucket for 12 months. Judged results are cached in Postgres keyed by hash(prompt bytes, model id, effort, judge schema), so an identical regrade returns identical judged output without a new call. Refusals, 429 and 5xx with jittered backoff, and timeouts are infrastructure outcomes recorded in an errors sidecar; a provider outage or the kill switch degrades to deterministic-only with judged criteria pending and automatic backfill oldest-first. Regrades, calibration runs and the eval harness use the Message Batches API (50 percent off, keyed by custom_id, results in any order) and never the interactive path. S4 aggregation [deterministic, pure]: scoring functions (step, banded_max_metric with GRD-03 severities and fraction scaling only within the passing region, linear_margin, level_map {0:0, 1:40, 2:75, 3:100}, archetype formulas from GAP3), weights from the per-archetype activation matrix, gates applied in documented order (fail-task, then caps: critical 50, major strength or loads 75, unsafe approval of the governing failing member 75, Optimize feasibility gate to 0 on economy), rounding, confidence = 0.35 judge_conf + 0.20 evidence_completeness + 0.15 (1 - retries/2) + 0.15 min(1, |total - threshold| / 10) + 0.15 memo_signal, and flags; totals are recomputed from stored rows on display and never trusted from a stored aggregate; the grade_version row stores criterion_scores with source (deterministic | judge | instructor | carried) and evidence_refs, every pin, and grade_hash. S5 review [human]: summative grades always enter the instructor or TA queue (R11) ordered by flag severity, confidence and age; formative tasks release deterministic results immediately with the narrative labelled AI-provisional; the review screen shows the 3D evidence overlay driven by visual payloads, the archetype comparison table (Analyze per-field submitted, reference and own-model values; Check key-versus-report matrix; Diagnose seeded errors with found, fixed and collateral status; Design and Optimize evidence and memo claim verdicts), judge rationale and memo claim verdicts; entry-level adjudication and per-criterion overrides require a reason and create a new grade_version (supersedes, regrade_reason instructor_override) through the same aggregation; bulk accept is offered only for unflagged grades above the tenant confidence threshold; release is atomic per task and emits bridle.aig.grade.released; appeals are v1.x but regrade requests reuse the version mechanics. Reproducibility and audit: deterministic stages are pure functions of the pin set, so replaying S1, S2 and S4 for any grade must reproduce result_hash, evidence_hash and the deterministic criterion scores exactly; a replay bundle (submission pin set, model revision, scenario instance, every ArtifactRef manifest with digest, evidence, judge request and output hashes with stored outputs) exports within 60 s; a nightly job replays a sample of released grades (and, in staging, every grade pinned to a newly promoted artifact) and pages on any inequality; regrades never edit rows, they append versions with a reason from the closed list and only the re-pinnable fields may change (never learner_id, model_hash, scenario_hash, task_version_id, content_version_id, justification_hash or attachments). Latency budgets: S0 at most 2 s with the receipt returned under 2 s p95; S1 plus S2 p95 at most 10 s for Tier M with 20 combinations; deterministic evidence visible within 15 s; S3 p95 at most 60 s including validator and one regeneration; end-to-end p95 at most 90 s at normal load and 20 min under the 500-submissions-in-5-minutes burst; stage hard ceilings at 3x the budgets move a job to the dead-letter queue.

## Jobs and queues

Technology: BullMQ 5 on Redis 7 with one logical queue per lane, a grading_job mirror row per job in Postgres for the inspector, and a transactional outbox for events. Queues and lanes: grading (deterministic stages S0 to S2 and S4; priority 1 interactive grading, priority 2 regrade and batch; per-worker concurrency 4; each S1 or S2 execution spawns bridle-runner with limits); judge (S3 only; concurrency governed by an adaptive limiter that backs off on 429 and 529 and never fails a grade; its own deployment so provider latency cannot starve deterministic work); analysis (learner Run on server and author calibration analyses; queue wait p95 at most 10 s; per-user cap 2 concurrent, per-tenant cap 50); calibration (PV-02 runs: references and 20 seeds through the full dry-run pipeline at batch priority); projections (outbox consumers for gradebook, progress, notifications, analytics and audit shipping); retention (daily purge or pseudonymize per class with a report); replay (nightly reproducibility sample and artifact-promotion replay in staging); integrity (similarity job after close; v1.x). Fairness and limits (SBX-03 trimmed to the MVP guardrails): a priority queue with per-tenant and per-user caps implemented as Redis token semaphores checked before a worker takes a job; a small fixed pool (2 to 6 grading workers, 1 to 2 judge workers) scaled by queue depth within the fixed ceiling; the batch lane may be delayed up to 60 min; an alert fires if any job waits more than 15 min. Idempotency: job id = hash(submission_id, pinset_id, grader_ref); duplicate submits return the existing job; every stage writes its output row before acknowledging, so a crash mid-stage resumes at the failed stage with the same pins; re-running a completed job creates a new grade version, never a second grade for the same version (integration test runs a job three times and asserts one version per run). Retries and stage budgets: infrastructure errors retry up to 3 times with jittered backoff; model validation and solver errors do not retry but complete the job with analysis_error evidence; stage budgets S0 5 s, S1 60 s, S2 30 s, S3 300 s, S4 5 s with 3x hard ceilings; a stage that exceeds its ceiling or exhausts retries moves to the dead-letter queue with a classified reason (solver_error, model_validation_error, llm_error, infrastructure, unknown) and the full payload; dead-letter entries are replayable individually or in bulk from the console and removed only on success or an audited discard. Reconciliation: every 15 min a job asserts that each submission version has exactly one active or terminal grading job and that each terminal job has a grade version, a dead-letter entry or an audited cancellation; violations page on-call, missing jobs are recreated with the original submit timestamp preserved for the late policy, and the lost-work counter on the exit-criteria dashboard increments only when a learner-visible loss is confirmed. Runner sandbox: bridle-runner runs as a subprocess in the grading worker container (read-only root FS, non-root user, no egress except VPC endpoints for S3, Postgres and Redis; only the judge service can reach the Anthropic API); Wasmtime fuel and memory limits make cancellation deterministic and the wasm module has no network or filesystem imports at all; worker images are pinned by digest and rebuilt weekly. LLM controls: per-tenant monthly budget with an 80 percent alert and hard stop, one global spend cap, per-route disable (bumps grader_version) and a global kill switch that stops new calls within 60 s, degrades to deterministic-only with judged criteria pending (never failed jobs) and backfills oldest-first on clearing (a 500-job backlog within 60 min); Batches API for regrades, calibration and the harness. Deadline windows ([due - 48 h, due + 24 h] per summative activity, extensions included) are recomputed nightly and on due-date change and drive change freezes, severity escalation and the 1-hour prompt-cache TTL. Schedules: outbox publisher every 500 ms; reconciliation every 15 min; retention daily; replay nightly; deadline-window recompute nightly; cost rollup hourly; weekly harness run in batch.

## Security and tenancy

Tenancy: every tenant-scoped table carries tenant_id and a Postgres RLS policy; the API opens each transaction with SET LOCAL app.tenant_id and app.actor_id from the verified session and the application role cannot bypass RLS (only the migration role can); a CI test fails if any tenant-scoped table lacks a policy, and the two-tenant authorization suite exercises every route as every role expecting zero unauthorized 2xx (any IDOR-class finding blocks a release). Global tables (users, artifacts, licensing register, flag registry) are not tenant-scoped; users join tenants through memberships. Object keys are tenant-prefixed and served only through signed URLs expiring within 15 min; similarity, calibration and analytics never cross tenants; tenant.region is stored and fixed to 'us' at MVP. Roles and authorization: learner, TA, instructor, author, institution admin and platform admin granted within scopes (platform, organization, offering, section); the permission matrix is data (apps/api/src/authz/permission-matrix.json) enforced by one authorize(actor, action, scope) function and mirrored in the UI; document access is one pure function over ownership fields, caller role, team membership and share grants (GAP6-01); TAs are section-scoped; authors never see learner grades; platform admins reach tenant data only through read-only view-as or consent-token impersonation with reason, time box (60 min default, 4 h max), a server-side denylist (no password, email, MFA, release, deletion or billing changes) and a learner summary email within 15 min. Authentication (R12): email and password per NIST 800-63B (argon2id, at least 12 characters, breached-password check, progressive delay, 15-min lock after 10 failures per account and IP), Google and Microsoft OIDC with verified-email linking, TOTP and passkey (WebAuthn) MFA enforced for instructor, author and admin roles with no bypass; sessions in httpOnly Secure SameSite=Lax cookies backed by a server-side store with revocation effective within 60 s, idle timeout 12 h for learners and 2 h for admins, absolute lifetime 30 days; all auth events audited. Integrity of records: submissions, model revisions, result sets, evidence, grade versions, scenario instances, artifacts and events are content-immutable tables with REVOKE UPDATE/DELETE for application roles plus triggers; grades and pin sets are append-only versions with reasons; audit events are written in the same transaction as the action (a failed audit write fails the request), carry prevhash, and are shipped to an S3 Object Lock bucket in compliance mode retained at least 7 years; every read of another person's education record (console, review, impersonation, export) emits bridle.plt.record.disclosed to satisfy 34 CFR 99.32, and learners can obtain their disclosure log. AI boundary: the judge receives only the evidence digest, rubric descriptors and the scrubbed memo inside untrusted-data delimiters in the user turn; no names, emails, ids, roster, grade history, reference geometry or standard text ever enters a prompt (an automated zero-PII test on the memo fixtures runs on every build; prompt and retrieval sources are restricted to the signed pack bundle); JudgeResult has no field that can touch an auto-scored criterion; deterministic caps bound every total; the Haiku pre-screen plus regexes flag instruction-like text to the integrity queue with neutral learner messaging; a red-team suite of at least 50 injection twins gates grader promotion at 99 percent identical scores; the AI is never described as an engineer, PE, SE or certified. Prompt and response logs are encrypted with a dedicated KMS key, access-logged and retained 12 months; the provider agreement provides no training on inputs and the shortest available retention for the pinned models; claude-fable-5-1 is excluded from the grading path. Secrets live in AWS Secrets Manager and are injected at runtime, rotated within 90 days; gitleaks pre-commit and CI; SCA, SAST and container scanning on every PR with critical CVEs fixed within 7 days; a CycloneDX SBOM per release; copyleft forbidden in the client bundle. Web security: nonce-based strict CSP, HSTS, SRI on CDN assets, Secure cookies; no COOP/COEP cross-origin isolation because the wasm core is single-threaded (recorded as an ADR so LTI iframes and video embeds work in v1.x). Abuse limits: per-user, per-IP and per-tenant rate limits at the API and in the queue, model-size caps checked before queueing, per-task submission quotas (default 10), result caching by hash so repeated identical analyses cost nothing, and a cost guard pausing a tenant above 150 percent of its daily compute budget. Privacy and retention: FERPA school-official posture; per-class retention (analytics 13 months pseudonymous with per-tenant HMAC keys in KMS; audit at least 7 years; learning 5 years after the offering concludes then pseudonymize; process 30 days with op-log segments 90 days unless referenced by a submission; LLM logs 12 months; diagnostic bundles 90 days) enforced by daily jobs with monthly reports; DSAR export within 72 h and erasure within 30 days in primary stores and 90 days in backups with pseudonymization of retained grade rows and a completion certificate; learner exemplar and calibration use only with recorded consent; disclaimer strings D1 to D5 asserted by automated tests on workspace, feedback panels, exports, certificates and API envelopes. Exam mode: data-bearing restrictions (hints, self-check, checks artifact delivery, exports, share links, discussion listing, ops after close, single active session) are refused at the API with an audited exam_mode error and recorded in a per-submission attestation; never client-only. Compliance baseline: full OWASP ASVS 5.0 L1 plus the L2 authentication, access-control and data-protection controls mapped in docs/security/asvs.md before the first pilot; HECVAT Lite and a draft VPAT before the first institutional contract; an annual third-party pentest from v1.x.

Pilot scale (3 tenants, about 100 learners, 6 to 8 summative tasks, about 3 attempts each, 100 percent review): about 2,500 judged grades per term, roughly 450 dollars of LLM spend per term, plus a weekly harness run of 100 fixtures x 3 repeats in batch (about 30 dollars per week). Storage per active learner stays under 50 MB per year: revisions are deduplicated by content hash (about 50 KB each), op-log segments reduce to summaries after 90 days unless referenced, prompt logs are deleted after 12 months. COGS per active learner-month at pilot volume is dominated by the fixed baseline (about 8 dollars at 100 learners) and falls under 2.50 dollars above roughly 400 active learners; the levers are the fixed worker ceiling, cache read share (target at least 60 percent, alert under 30) and per-tenant LLM budgets with a global cap. Engineering: about 105 engineer-weeks of build plus design-partner content effort; two independent PE or SE reviewers under framework agreements for pack verification; outside counsel for the licensing register, ToS and the pilot agreement.

## Answers to open questions

Q1 Launch geography and second pack: US pilot first (default kept). Reasons: the US pack has the most freely available reference data (AISC 360-22 downloadable, AISC Design Examples for verification, USGS public-domain seismic values), the design-partner instructors and the ADA and FERPA procurement path are US, and the licensing position is clearest. Recommended second pack: NSCP 2015 (7th edition), unless the first non-US customer is European: the founding team's market includes the Philippines, NSCP reuses the AISC and ACI derived member checks so it exercises the actions and combinations stages of the Pack trait (UBC-97 seismic with Z, Na/Nv, Ca/Cv and f1 in combinations) with the least new member-check code, and the ASEP permission request (GAP2-LIC-08) must start in month one to be ready for v1.x. Eurocode (first generation with a UK National Annex overlay) follows as the third pack. The conformance suite ships at MVP with EN 1990 and NSCP 203 fixtures so the trait is proven against both philosophies before either pack is built. Q2 Backend language: TypeScript end to end for web, API, workers and the grader, plus the Rust core; no Python services. Reasons: everything that must be deterministic already lives in Rust and is reused by both sides, so a Python grading or solver service would add a third runtime without adding determinism; one schema package generates both TypeScript and Rust types; the Anthropic TypeScript SDK supports structured outputs, batches and prompt caching; one toolchain keeps a four-to-five-person team's CI under 12 minutes. Python is allowed only as offline tooling in tools/verification for the OpenSees cross-check and is never deployed. Q3 Hosting: one provider, AWS, single region us-east-2 at MVP: RDS Postgres 16 Multi-AZ with PITR, ElastiCache Redis 7, S3 with Object Lock (the WORM audit requirement rules out simpler PaaS hosts), KMS and Secrets Manager, ECS Fargate for web, api and workers, CloudFront and WAF, all defined in OpenTofu with apply-from-CI. GCP would serve equally (Cloud SQL, Memorystore, GCS bucket lock, Cloud Run) but AWS has broader university procurement familiarity and the cleaner VPC-endpoint story for a network-isolated runner; Fly, Render and Vercel were rejected for lack of WORM storage, PITR control and private networking. The EU region in v1.x is a second OpenTofu stack with EU-resident data and inference_geo set on judge calls; tenant.region is stored from day one so no schema change is needed.

## Trade-offs

Pros:
- Bit-identical browser and server results by construction: the same wasm bytes run under V8 and Wasmtime with deterministic float semantics and libm, so the R7 integrity check is equality rather than a tolerance and the grader can prove it shows what the learner saw.
- One implementation of every numeric and canonical rule (solver, checks, derivation, seeds, deliverable scoring, canonicalization) with schemas generated from one source, so there is no TypeScript-versus-Rust drift and no second hashing code path.
- Reproducible, auditable grades: full pin sets on submissions and grades, content-addressed artifacts with gates, hashed evidence, replay bundles, append-only versions with closed regrade reasons, and a nightly replay that monitors the property.
- Cheap compute: course-sized models solve in milliseconds, server work is one cached re-analysis per submission, and the baseline footprint stays well under the 1,000 dollars per month target.
- Boring, well-understood infrastructure (Next.js, Fastify, Postgres with RLS, Redis and BullMQ, S3, ECS Fargate, OpenTofu) that a four-to-five-person team can operate.
- Packs as data plus a Rust module behind a six-stage trait with a conformance suite that already contains EN 1990 and NSCP fixtures, so the second pack is additive and licensing is gated at build time.
- The GradeEvidence schema is the single contract across self-check, grader, review UI, learner feedback, help pages and analytics, so what the self-check shows is exactly what the grader finds.
- The LLM is fenced: judged criteria only, grounded in a deterministic digest, schema-constrained with no auto-score field, validated, cached by prompt hash, stored verbatim with request and output hashes, and gated by an offline harness.
- Schema seams for teams, integrity and collaboration (ownership fields, actor-stamped invertible ops, stable ids, one anchor model, pin sets) are in the MVP schema, so v1.x features need no migration of stored documents.

Cons:
- Two languages (Rust and TypeScript) plus a wasm toolchain on a small team; the engine is a bounded but specialist workstream.
- Running the grading engine as wasm under Wasmtime is roughly 1.5 to 2x slower than native and single-threaded; fine for S and M tiers but the L tier and large analyses need the native path with documented tolerances in v1.x.
- One wasm binary couples engine, checks, scenario and canon versions: a checks-only fix still produces a new engine digest and a re-pin decision, mitigated by pins-only task versions and regrade_policy none.
- Data-only packs plus Rust check modules mean a new check or a new code family requires an engineering release and SME verification; instructors cannot add deterministic checks themselves at MVP.
- 100 percent human review of summative grades and Opus 5.5 on every judged route make instructor workload and per-grade cost higher than a confidence-routed, Sonnet-based design; this is the price of the calibration data needed to earn auto-release later.
- Single US region and no LTI, SAML or SCIM at MVP limit which institutions can pilot and force CSV gradebook export for one term.
- Strict immutability and pin-set breadth add schema and registry work before the first feature ships, and append-only storage requires retention tooling from day one.
- Deferring canary deploys, preview environments and the device-calibrated tier router keeps the MVP small but leaves rollback manual and the live loop dependent on the per-task cap being set well.

## Risks

| risk | mitigation |
|---|---|
| faer-sparse does not build or perform on wasm32-unknown-unknown. | Week-1 spike with a pass/fail bar (10-storey 6x6-bay frame, about 3.2k DOF, under 50 ms in Chrome); fallback is an in-house CSparse-style simplicial LDLT with AMD (about 2k lines), sufficient for S and M tiers; the benchmark suite exists from day one so either path is verified the same way. |
| A hidden host dependency (a JS Math import, NaN canonicalization, memory-growth order, SIMD lane semantics) breaks cross-host bit-identity. | The wasm module imports nothing but memory and a log sink; libm for all transcendentals; non-finite values are errors; the CI matrix runs every benchmark under V8, SpiderMonkey, JavaScriptCore and Wasmtime on every change; a runtime mismatch is a platform_fault routed to review, never a learner error. |
| Wasm-under-Wasmtime grading or calibration bursts (20 seeds times references times templates) exceed the deterministic-stage budget. | Fuel-measured budgets and the batch lane for calibration; Tier-M solve is about 0.3 s so 20 seeds fit in minutes; the per-task cap keeps models in tier; the native path with documented tolerances is the v1.x escape hatch for the L tier. |
| Single-binary coupling causes frequent re-pins and regrade churn after small fixes. | Pins-only task versions keep published versions immutable; regrade_policy defaults to none; per-crate changelogs in the manifest; staged rollout rings; checks-only changes ship as PATCH releases with full regression and SME re-verification of changed checks only. |
| A code-check defect is found after grades are released. | Signed PE or SE verification record per pack version, worked-example suite and golden submissions in CI, grade provenance on every score, replay job to enumerate affected submissions within 24 h, bulk re-pin with grade quarantine and instructor release, S1 errata SLA (institution disclosure in 2 business days, regrade offer in 10). |

| Prompt injection or hallucinated numbers and clauses in feedback. | Structured outputs with no auto-score field, grounding validator with template fallback, untrusted-data framing in the user turn only, Haiku pre-screen, clause ids validated against the pinned library, red-team suite gating promotion at 99 percent identical scores. |
