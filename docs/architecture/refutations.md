# Adversarial refutations of the synthesized architecture

Two reviewers attacked the first synthesis; the final document answers each issue (see change-log.md).

## Lens: Performance and determinism skeptic: latency budgets, browser/server bit-identity, canon/1 hashing, size tiers, queue and worker sizing, verification plan

No fatal flaw. The claim the design rests on, bit-identical results across wasm hosts for one artifact, is sound in principle (wasm f64 and simd128 arithmetic is deterministic outside relaxed SIMD and NaN payloads, and every transcendental lives inside the module), but the design around it is weaker than the text says: the incremental live engine is never required to produce the same bits as the server's fresh solve (and quantization does not absorb ulp-level differences at Tier M, so the exact result_match check would page routinely), the hash-only submission cannot support the promised tolerance path, the JCS result canonical form is 30-80 MB per Tier-M result set, and the cross-host hash gate only ever runs the dense (<500 DOF) path. The latency and sizing numbers are mostly asserted rather than derived: the Tier-M 300 ms p95 extrapolates from the inputs' own 3.2k-DOF datapoint to 0.4-1 s at the cap, the 1.5 s per job omits Wasmtime compilation, the 30 s judge call and 21-minute burst are unmeasured against Opus 5.5 output speed and tier limits (no Priority Tier exists for it), and Postgres and web-tier sizing have no write-rate model behind per-op rows and 5-second segments. Ten major and seven minor issues, each with a fix that fits the existing components; the biggest process gap is that the live budget and the judge latency are never measured before the first real deadline. Foreman note: the relayed user message about the build-monitor dashboard UI is unrelated to this step and already shipped as Monitor v3 (commit fdb22a2); nothing here touches it.

### Major (10)

- **Tier M (<= 2,000 members, about 12,000 DOF) solves in 120 ms p50 / 220 ms p95 in the browser and commit-to-pixels is 300 ms p95 (sections 7-8, binding as R14).**: No derivation is given for any Tier-M number. The only derived datapoint in the inputs is the FE domain's 10-storey frame (3.2k DOF, nnz(L) 1-2M, ~1e8 flops), which the FE doc prices at 20-40 ms but which at its own stated 1.5-3 GFLOP/s wasm rate is 33-67 ms. Sparse LDLT work grows superlinearly on frame graphs (n^1.5 to n^2), so 12k DOF is 4e8-1.4e9 flops: 0.2-0.7 s for numeric factorization alone, before 20-50 right-hand sides (2*nnz(L) each), station recovery, checks and the result copy. The FE doc's own tier table puts 6k-12k DOF in Tier 2 (background with progress, < 3 s) and the NFR doc's live tier is <= 2k DOF; the architecture collapsed Tier 2 into 'live M' while keeping a 300 ms promise, and it gives no per-browser number although the reference laptop includes M1 MacBooks on Safari, whose wasm numeric throughput typically trails V8. The number is now ADR-binding and cannot be met at the cap. Evidence: 02 Domain notes 2 (3.2k DOF ~1e8 flops; Tier 1 <= 6k DOF frames, Tier 2 6k-60k DOF) and SIM-NFR-01; 06 PERF-04 (live <= 2,000 DOF <= 100 ms, large-browser <= 20k DOF <= 1.5 s); architecture section 7 'about 12,000 DOF' and section 8 budget table; ADR R14. Fix: Define live Tier M by predicted work from the symbolic analysis both sides already run: estimate() returns dof, nnz(L) and flops, live mode requires flops <= a calibrated constant (start near 2e8, twice the 3.2k-DOF frame) and dof <= 6,000; the 6k-12k DOF band is 'Run mode with progress', which the architecture already has as the above-live fallback. Attach the R14 contract to two committed reference scenes (S: 2D frame <= 200 members; M: 10-storey 6x6 frame, ~1.3k members / 3.2k DOF, 20 combinations) and amend R14 to say so. Make the week-1 spike measure the Tier-M cap scene on M1/Safari and Tiger Lake/Chrome, not only the 3.2k-DOF frame in Chrome. Superpose combinations on demand instead of solving and transferring all of them per edit.
- **result_match is 'exact' when artifacts match; any mismatch raises a platform_fault signal routed to review as a system error and the host-mismatch counter pages.**: The Engine Worker produces results through an incremental engine (applyOps, factorization reuse for load-only edits, symbolic reuse for geometry edits) while bridle-runner solves the canonical model from scratch. Cross-host bit-identity holds for the same arithmetic sequence; it does not hold between an in-place-updated stiffness matrix or factor and a fresh assembly, because floating-point addition is not associative: (k1+k2+k3_old) - k3_old + k3_new differs from k1+k2+k3_new by ulps. Quantization does not absorb this: a 100 kN force perturbed by ~1e-10 N against a 1e-3 N quantum straddles a rounding boundary with probability ~1e-7 per value; a Tier-M result set has ~2.6M force and moment values for 20 combinations, so 20-50% of well-conditioned Tier-M submissions would hash differently and essentially all ill-conditioned student models (condition 1e6-1e12 amplifies the perturbation) would. Each becomes a paged platform fault and a review-queue system error, and the self-check parity assertion (evidence_hash equality for every template) is fragile for the same reason. The architecture never states the invariant that would prevent this. Evidence: Architecture 4.2 (applyOps), 7 ('factorization reuse ... symbolic reuse'), 10 S1 result_match, 14 'host mismatch counter (paged as a system error)'; 02 SIM-ARCH-05 (engine keeps internal state and accepts diffs) and SIM-DET-01 recipe (silent on incremental state); 09 DM-11; 11 DLV-16 and NF-GAP3-07. Fix: (a) State and test an engine invariant: every solve re-assembles K from the canonical sorted entity list (O(members), 1-2 ms at Tier M); symbolic ordering is reused only when the adjacency graph is unchanged (AMD is deterministic for an identical graph); the numeric factor is reused only when the newly assembled K is byte-identical to the previous one. (b) At submit the worker computes client_result_hash from a fresh load-plus-solve of the canonical model through the same code path the runner uses. (c) CI property test: 1,000 random op sequences, hash(incremental solve) == hash(fresh solve of the final canonical model), on all five wasm hosts. (d) Keep 'exact' as the normal outcome but classify a sub-tolerance difference as within_tolerance with a metric and page only on beyond-tolerance mismatches (which requires the next fix).
- **result_match is computed 'within_tolerance at 1e-6' when the engine artifacts differ.**: A tolerance comparison needs the client's values. The submission pin set carries only client_result_hash plus a display-only summary (DM-05, R7), the bundle is capped at 5 MB, and a Tier-M result set is tens of MB. So the within_tolerance outcome is not computable as specified, and the mid-offering engine-upgrade case that R7 reserves tolerance for degrades to not_compared or to a false mismatch. Evidence: Architecture 5 (submissions row), 10 S1, 11 (POST /submissions receipt); ADR R7; 09 DM-05 (client_result_hash only) versus DM-11 ('compares the learner's client results with the server rerun by tolerance'); 03 CAP-02 (bundle <= 5 MB). Fix: Define a compact canonical client result summary document (kind result_summary: per combination the reactions per support, max |u| per node direction, governing utilization and station per member, equilibrium residuals; a few hundred KB at Tier M, quantized with the result quanta) that the worker computes from the fresh submit-time solve and includes in the bundle with its hash. Exact-compare the full result_hash when artifacts match; tolerance-compare the summary when artifacts differ or the full hashes differ; record which comparison ran. This also provides the 'show both values' evidence the AIG risk table asks for.
- **canon/1 quantization (listed quanta, dimensionless 1e-6) yields a model_hash that identifies the model the solver analyzes, and result sets are cached by (model_hash, scenario_hash, engine_ref, numeric_profile, analysis_options_hash).**: Nothing says the solver consumes the dequantized canonical form; the natural reading (loadModel(model) in the Worker Protocol, model.json in the job directory) is that browser and runner solve the raw revision while model_hash is taken over the quantized projection. The cache key is then coarser than the solver input: two raw models differing below a quantum share a model_hash and the second is served the first's cached results and evidence. The quantum table makes this non-negligible for at least one field: thermal expansion alpha (~1.2e-5 /K) has no quantum of its own and falls under dimensionless 1e-6, so 1.17e-5 and 1.2e-5 collide, a 2.5% change in E*alpha*dT for the temperature criterion. The table also lacks quanta for warping constant Cw (m^6, in the schema), temperature gradient (K/m) and 1/K, and has no overflow rule for counts >= 2^53 (the 1e-14 m^4 quantum overflows at 90 m^4). Each gap is a silent canonicalization error or a hash-collision class. Evidence: Architecture 6 (canon/1 and quanta), 4.2 (loadModel/applyOps), 4.5 (model.json), 10 S1 cache key; 09 DM-10 (quanta, |n| < 2^53); 02 schema outline (Cw, alpha in sections and materials). Fix: State the invariant 'analysis input = dequantize(canonicalize(model)) on both sides' and add a golden test solve(raw) == solve(canon(raw)) for every template. Add per-field quantum overrides in the schemars annotations (alpha 1e-12 /K, Cw 1e-18 m^6, gradients 1e-6 K/m, strain and damping 1e-9). Make the canonicalizer error on counts >= 2^53 and on any numeric field without a quantum, enforced by a CI test that walks the schema.
- **The result canonical form is JCS of every quantized output sorted by (combination, entity, station), hashed with SHA-256 and stored in S3; S1 plus S2 is <= 10 s p95 for Tier M and server analysis costs about $0.0005 per regrade.**: Scaled out: Tier M is 2,000 members x 11 stations x (6 forces + 3 deflections) = ~200k values per combination; 20 combinations give 4M values and the full ASCE 7-22 set with W and E expanded by direction and sign plus service sets (40-50 combinations) gives ~10M. As JCS text that is 30-80 MB per result set, and JCS serialization plus SHA-256 of that in wasm is on the order of 1-3 s per job on one vCPU, which is the entire 1.5 s per submission the burst math assumes. Stored as result.f64 it is 32-80 MB per result set, about 90 GB per 200-learner term (1,800 grades) before the 30-day cache, against COST-01's 50 MB per active learner-year. None of this appears in the S1 budget or the cost table. Evidence: Architecture 4.5 (result.f64 output), 6 (result canonical form), 10 S1, 12 burst math, 14 cost; 06 COST-01; 01 CODE-02 (full direction and sign expansion of combinations); 02 Domain notes 4 ('resultHash (hash of canonical little-endian f64 arrays)'). Fix: Hash the result as the quantized int64 little-endian array in canonical order (the FE doc's own formulation) and reserve JCS for small documents (model, scenario, evidence, submission, grade). Store case results only (combinations and envelopes are superposition, recomputable under the pinned artifact), varint plus zstd compressed (~2-3 bytes per value), default 11 stations only. Re-derive S1 time and storage per tier from these sizes and put them in section 14.
- **Each solve spawns bridle-runner (Wasmtime with fuel, memory and epoch limits); a Tier-M submission costs about 1.5 s; 500 submissions over 4 slots take about 190 s.**: A fresh wasmtime process must Cranelift-compile engine.wasm and checks.wasm (<= 1.5 MB each) before running; on a single Fargate vCPU that is on the order of 0.5-2 s per spawn, plus pack-bundle loading and the constant overhead of fuel metering on every loop. None of this is in the 1.5 s, so the real per-job time is roughly 2-3.5 s, the burst time doubles (about 380 s at 4 slots, 190 s at the burst ceiling), most of the 10-minute deterministic target is consumed, and the 60 s p95 that OPS-12 alarms on is exceeded at every deadline. Precompilation is never mentioned. Evidence: Architecture 4.5 (invocation per op, fuel/memory/epoch), 4.6 ('each solve spawns bridle-runner'), 12 burst math and alert thresholds; 12 OPS-12 detection ('grading-lane p95 wait above 60 s'); 05 NFR-01. Fix: Precompile each promoted artifact once per (artifact digest, wasmtime version, target CPU) with wasmtime compile and ship or cache the .cwasm (deserialize is milliseconds), or keep one warm runner process per slot that instantiates both modules once and serves jobs over the job-directory contract with a fresh Store, fresh linear memory and epoch deadline per job. Use epoch interruption for the wall limit and keep fuel as the deterministic work meter for CI. Re-run the burst arithmetic with measured spawn, compile and solve times and set the OPS-12 threshold from the result.
- **Judge calls take about 30 s each, so 500 submissions drain through concurrency 12 in about 21 minutes; the judge stage is <= 60 s p95; the median grade costs about $0.14.**: 30 s per call for about 5.5k output tokens (adaptive thinking plus a merged criteria-and-narrative JudgeOutput at effort high, max_tokens 12,000) implies ~185 output tokens per second sustained from Opus 5.5 on every call, and no measurement is cited. The stage also includes a Haiku screen, a count_tokens call and up to one regeneration (a second full Opus generation), so the p95 path is two Opus calls. If a call takes 60-120 s the burst drains in 40-80 minutes, not 21, and a 60 s stage p95 is unreachable. Rate limits are per-model, per-tier pools (Opus 5.5 has its own) and Priority Tier is not offered for Opus 5.5, so deadline capacity cannot be bought; the architecture never checks the implied ~300k input and ~60k output tokens per minute at concurrency 12 against the org's tier. The staging burst rehearsal runs the judge in replay mode, so none of this is measured before the first real deadline. Evidence: Architecture 4.14, 10 S3 budget, 12 burst math, 15 (staging 'grader eval in replay mode plus a weekly live run capped at $25'); claude-api reference: Opus 5.5 separate rate-limit pool, Priority Tier excluded for Opus 5.5, fast mode sold at 2x price for up to 2.5x output speed (standard output speed is bounded); 06 SCL-02 (AI feedback 95% within 30 min); 05 NFR-02. Fix: In the first week of step 10 run about 50 golden grades live at concurrency 12 (roughly $10) and record p50/p95 call latency, output tokens, cache reads and 429 behaviour; re-derive the burst table from measured numbers; request the Opus 5.5 tier increase the deadline concurrency needs before the first pilot; set the SLO the data supports (deterministic within 10 min, judged 95% within 60 min unless measured better) and split the narrative into a separate call only if the merged output length is what breaks latency; include a capped live-judge slice in the 500-in-5-minutes rehearsal.
- **CI asserts identical result_hash on the benchmark suite across Node, Wasmtime, Chromium, Firefox and WebKit, and engine promotion requires identical hashes across all wasm hosts on that suite.**: The benchmark suite is 25 closed-form problems (cantilever, simply supported, portal sway, Warren truss, beam on springs...) of tens to a few hundred DOF, which the engine routes to the dense path (< 500 DOF). The sparse AMD/LDLT path, the simd128 kernels, iterative refinement and Tier-M-scale station recovery, the code that actually runs for graded coursework, are never exercised by the cross-host gate, so a host-dependent bit in that path would pass promotion. The AISC capacity reproductions are checks-only and tolerance-compared, so they do not cover it either. Evidence: Architecture 7 ('dense path under 500 DOF'; verification list of 25 closed-form problems; 'CI asserts identical result_hash on the benchmark suite'), 4.11 engine gate; 02 SIM-DET-01 acceptance (benchmark suite only). Fix: Add to the cross-host hash gate: the performance scenes (3.2k-DOF frame and the Tier-M cap scene), all eight templates at S and M, three deliberately ill-conditioned fixtures (1e18 spring, 1 mm member, released chain) and a nightly seeded 1,000-model random corpus, hashed on all five wasm hosts; native stays tolerance-only and informational.
- **RDS db.t4g.medium Multi-AZ (2 vCPU, 4 GB) holds every entity, pg-boss, the events table and per-op rows (ops with before/after JSONB), with op-log segments every 5 s or 500 ops; the web tier is 2 x 1 vCPU, all for about $140 and $70 per month.**: No write-rate derivation exists. At the SCL-01 target of 500 concurrent live workspaces, 5-second segments are ~100 POSTs/s to the web tier (auth, RLS transaction and S3 put each) and, with per-op rows, 150-500 row inserts/s carrying before/after JSONB (a bulk section change on 500 members carries 10 KB or more per op): 6-20 GB/day and 0.5-2 TB over the 90-day process retention on an instance with 4 GB RAM that is also the queue, the outbox and the projection source. Any learning or analytics event emitted per live solve (MET-01 analysis_run) would add thousands of rows per second. The RDS line and the 2-vCPU web tier are asserted, not sized. Evidence: Architecture 4.1, 4.3 (segments every 5 s or 500 ops), 4.12, 5 (ops and oplog_segments rows with before/after), 14 cost; 06 SCL-01 (500 concurrent sessions), AVL-03 (server save <= 10 s); 09 DM-21 and DM-NFR-04; 08 MET-01 (analysis_run event). Fix: Ops live only inside S3 segments (content-addressed and hash-chained, already in the design); Postgres keeps one row per segment (document_id, seq range, sha256, prev_hash, s3_key). Segment cadence 30-60 s while editing, flushed on blur, tab hide and submit; IndexedDB already bounds crash loss at <= 2 s and the <= 10 s server-save bound is met by coalesced model revisions, not per-op rows. Never emit a Postgres event per live solve: aggregate solve telemetry client-side into the RUM endpoint. Then size RDS and the web tier from measured ops/s per active session and req/s, and record the derivation in section 14.
- **The full solver suite runs nightly with a 15 percent timing gate, engine promotion requires a performance regression under 15 percent, and the budgets are reproduced in CI.**: Wall-clock timing on shared CI runners varies 20-50% run to run, so a 15 percent gate is either flaky (blocks releases spuriously) or gets waived, and no CI machine resembles the reference laptop (M1 or Iris Xe, Safari or Chrome), so the R14 live budget is unverified until RUM in production. The runner already meters Wasmtime fuel, which is a deterministic instruction count for a given artifact and wasmtime version. Evidence: Architecture 7 (verification and performance gates), 4.11, 15 CI; 06 TEST-01 ('timing cases gated at +/-10%'), PERF-02 reference machine. Fix: Make fuel consumed per benchmark the primary regression metric (zero noise; gate at 5 percent) with wall-clock reported informationally; run a weekly job on one self-hosted M1 Mac mini (Safari and Chrome) and one Tiger Lake laptop against the committed reference scenes and publish those numbers as the R14 evidence before the pilot.

### Minor (7)

- **Superseded solve requests are cancelled within 200 ms, a user cancel is honoured promptly, and the live solve budget is 5 s after which the run is cancelled.**: Without cross-origin isolation there is no SharedArrayBuffer, so a Web Worker executing a synchronous wasm solve cannot observe a cancel message until the solve returns; cancel latency equals solve duration. That is tolerable at Tier M (<= 300 ms) but the 5 s budget and SBX-01's 100 ms cancel cannot be enforced except by worker.terminate(), which discards the loaded modules, packs and factorization cache and costs a ~300 ms re-instantiation on every cancel. Evidence: Architecture 4.2 (cancel within 200 ms, 5 s budget, restart on panic), 20 ('COOP/COEP threading' deferred); 06 SBX-01 (user cancel within 100 ms); 02 SIM-ARCH-06. Fix: Structure the solve as resumable phases with state kept in wasm memory (assembly, symbolic, numeric factorization in column blocks, RHS batches, recovery) and return to the worker event loop between phases so queued cancel and newer-seq messages are observed at sub-50 ms granularity; terminate-and-restart stays as the last resort for panics only.
- **Scene rebuild costs 8 ms (S) / 20 ms (M) on the main thread while a Long Tasks assertion guarantees the main thread never blocks more than 16 ms.**: The two numbers contradict each other: a 20 ms synchronous buffer rebuild is by definition a long task over 16 ms, so the assertion fails on every Tier-M solve or is set so loosely that it protects nothing. The source requirements set 16 ms for engine activity (SIM-NFR-07) and 50 ms for solver work on the main thread (SBX-01), and the architecture picked the tighter one while budgeting the looser behaviour. Evidence: Architecture 4.2 (16 ms assertion) and 8 (scene 20 ms); 02 SIM-NFR-07; 06 SBX-01. Fix: Chunk overlay buffer rebuilds across frames (deformed shape first, diagrams and utilization next frame) or move geometry generation into the worker and transfer finished buffers; set the Long Tasks assertion to SBX-01's 50 ms for scene work and keep 16 ms for engine message handling.
- **Each solve returns all cases as a transferable Float64Array frame with 'transfer 10 ms', and case switching repaints cached results in under 100 ms.**: Transferring every case per edit means allocating and filling 20-80 MB per Tier-M solve (4-10M doubles) several times per second during interaction; transfer itself is zero-copy but the fill and the allocation churn on an 8 GB laptop are not, and the number of cases is uncapped per tier (the analyze lane allows 50 cases and 200 combinations). Evidence: Architecture 4.2 and 8 (transferable frame plus JSON index for all cases), 12 (analyze limits 50 cases, 200 combinations); 02 SIM-ARCH-05 (combination evaluation for 30 combos adds < 5 ms). Fix: Keep per-case results inside the worker; transfer only the active case or combination overlay (about 1 MB at Tier M) plus the per-member envelope summary; superpose combinations on demand in the worker (< 5 ms) when the user switches; cap live cases per tier in estimate().
- **bridle-cli (native) replay --grade <id> --assert re-executes S1, S2 and S4 and asserts result_hash and evidence_hash equality.**: The architecture itself compares native to wasm only by tolerance (1e-9) and makes the Wasmtime-hosted wasm artifact the sole authoritative host, so a native replay cannot assert hash equality; as written the assertion fails by design, or the CLI silently re-pins the engine to a native build that never graded anything. Evidence: Architecture 4.4 (bridle-cli native), 7 (native compared within 1e-9, 'authoritative execution host is the wasm artifact under Wasmtime'), 10 reproducibility paragraph; 09 DM-23. Fix: Make replay an orchestration command that drives bridle-runner (the wasm artifact by pinned digest) for S1 and S2 and the TypeScript grader package for S4; native bridle-fem is used only for bench and the informational tolerance comparison; also load canon-node by the task's pinned engine_ref and canon_version rather than one global digest so old hashes are recomputed under their recorded canon version.
- **Calibration generates a greedy auto-sized reference per seed (default 20 seeds) in the analyze lane with limits of 2,000 members, 50 cases and 200 combinations and no stated time budget.**: Greedy lightest-passing-section sizing re-solves and re-checks after every section change: at Tier M that is roughly 50 member groups x ~10 catalog steps = 500 solves x 1.5-3 s = 12-25 minutes per seed and 4-8 hours per task version on one slot, shared with the grading lane; the architecture gives no budget, no iteration cap and no reuse strategy for it. Evidence: Architecture 4.6 (analyze processor), 12 (analyze lane limits); ADR R10; 07 PV-02 (20 sampled seeds); 01 SITE-03 reasoning. Fix: Bound the greedy search (monotone search within a section family, symbolic reuse across iterations, stop when the heaviest member in each group reaches DC >= 0.7), run calibration in the batch lane with a stated per-task budget (for example 30 minutes at Tier S, 2 hours at Tier M) and surface the measured time in the calibration report.
- **About $0.14 median per judged grade from 12k cached input tokens, with a 60 percent steady-state cache read share and an alert when the read share drops below 30 percent for an hour.**: The task-block cache has a 5-minute TTL (1 hour only in deadline windows); a 200-learner pilot produces about 20 grades per day off-peak, so most judge calls outside deadline windows miss the task block and only the shared system block hits. Off-peak input is then ~15-18k uncached tokens, the median moves to roughly $0.18-0.20, and the 30-percent-for-an-hour alert fires every quiet afternoon. The 512-token minimum prefix itself is fine on Opus 5.5 and Haiku 5.5. Evidence: Architecture 10 S3 prompt layout and cache TTLs, 14 cost; claude-api reference (minimum cacheable prefix 512 tokens on Opus 5.5 / Haiku 5.5; 5-minute and 1-hour TTLs); 06 COST-02. Fix: Cost the median at the cold-task-cache input and the p95 at the regeneration path; scope the cache-share alert to deadline windows (or to tasks with >= 10 grades in the hour) and otherwise track it as a metric; consider the 1-hour TTL for the task block whenever a task has had a grade in the last hour.
- **Submission status and review-queue updates are delivered as SSE streams from Next.js route handlers on 2 x 1 vCPU web tasks.**: The fan-out mechanism is unspecified. If each stream polls Postgres (the only shared state), 500 learners watching status during a deadline produce ~250 RLS-scoped queries per second on the db.t4g.medium, and ALB's 60 s idle timeout drops idle streams without keepalives; neither the query load nor the keepalive appears in the design. Evidence: Architecture 4.1 (SSE from route handlers), 11 (GET /submissions/{id}/status SSE), 12 (pg-boss 500 ms polling); 06 PERF-05 (status updates < 2 s), SCL-01. Fix: One LISTEN/NOTIFY subscriber per web task (notified by the grading_jobs state-change trigger and the outbox relay) fanning out to in-process streams; 20-30 s SSE comment keepalives under the ALB idle timeout; a connection cap per user and a fallback to 5-second polling of a single projection when the stream cap is hit.


## Lens: Small-team delivery and cost skeptic: build sequence and estimates, hidden complexity in the Rust core and packs, operational burden, LLM cost per grade, vendor lock-in, and what a team of 3-5 cannot realistically own.

Nothing in the synthesis is unbuildable and the hard engineering choices (pg-boss in the submit transaction, Wasmtime runner isolation, content-addressed artifacts, deterministic-first grading, Postgres-and-S3-only state) are the right ones for four people. The two headline delivery claims do not survive arithmetic, though. The 121 engineer-week / eight-month plan under-counts the Rust-plus-structural critical path (steps 2-5 are about 29 ew that one or two Rust-capable engineers must do near-serially), the pack, solver, workspace, console and judge/harness steps are 1.5-2.5x thin, no focus factor is applied, and calibration content plus every externally gated item (pentest, SME sign-off, counsel, insurance) lands in the final step; as written it cannot produce the early-August production-ready date a fall-2027 pilot needs. The $0.14 median LLM cost omits cache-write pricing and the 5-minute-TTL warm requirement and rests on an unmeasured 5.5k-output-token assumption at effort high, so COST-02, tenant budgets and the 30-minute burst SLO are unverified; the pilot dollar amount stays small, but budgets sized from $0.14 would trip the 100% hard stop mid-term. Operationally, the op-log segment-per-object S3 path costs an order of magnitude more than the $30 line at the stated 500-session target, the pilot-term run regime (24x7 deadline windows, freezes, two-person promotions, office hours) is roughly one unbudgeted FTE, non-cloud launch costs are absent, and the retirement of pinned judge model ids has no runbook. No issue is fatal. Required before build: re-plan on a dated critical path with the cut list applied by default and either a contracted Rust/FE engineer or a spring-2028 pilot; measure judge cost and latency on 50 golden grades at effort medium and high; route formative judging through Message Batches; batch op-log segments; add a launch budget and external-dependency calendar; write the model-retirement runbook.

### Major (11)

- **"Total about 121 engineer-weeks: about eight months for four engineers (six and a half for five)", with the cut list "applied only if the academic calendar forces it" (section 17).**: Calendar time is not 121/4. Steps 2, 3, 4 and 5 are 29 ew of Rust-plus-structural work that only the one or two Rust-capable engineers can do, so they run near-serially (15-29 calendar weeks before the pack exists); steps 8 to 9 to 10 to 11 to 12 to 16 are declared serial dependencies totalling 45 ew; no focus factor is applied for on-call, pilot support, vacation or ramp; and several step estimates are thin on their own terms (foundations 7 ew for the full OpenTofu VPC/endpoints/ECS/RDS/Object-Lock footprint plus OIDC+TOTP+passkey auth plus the two-tenant every-role authorization suite; judge stage 6 ew for prompt assembly, the grounding validator, record/replay, a Batches client and a gated harness; console 7 ew for the entire OPS-01..16 surface; the better-auth fallback priced at one engineer-week for a module that must cover OIDC, TOTP, passkeys, sessions, lockout and breached-password checks). A realistic total is 180-200 ew, which at a 0.7 focus factor is 12-15 months for four engineers and misses the early-August production-ready date for a fall-2027 pilot by a full term. Evidence: Section 17 table and dependency column; section 18 risk row "Rust is the critical path for a TypeScript team"; PRD domain notes section 4: "a fall pilot must be production-ready by early August for a late-August start" and "pilot instructors need the course at least 6 weeks before term start"; MVP-01 "every task's rubric is calibrated on >= 10 golden submissions before the pilot starts"; OPS-11/HELP-04 run load not included anywhere in the estimate.
