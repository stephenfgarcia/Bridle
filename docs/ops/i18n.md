# Externalized UI strings

Requirement I18N-01 (docs/requirements/04-core-lms-courses-enrollment-grading-tracki.md): UI strings are
externalized as ICU MessageFormat, a lint fails the build on hard-coded user-facing strings, and a pseudo-locale
build shows truncation and untranslated strings. Card P0-02.6 put the first three pieces in place, before the
application has more than one page:

| Piece | Where |
|---|---|
| The message catalog | `packages/i18n/messages/en.json` (the source) and `packages/i18n/messages/en-XA.json` (generated, committed) |
| The lookup, `t("id", values)` | `packages/i18n/src/index.ts` (`@bridle/i18n`); `apps/web/src/i18n.ts` binds it to the locale of the build |
| The string lint | `packages/i18n/lint/lint-strings.mjs`, the second half of `pnpm lint`, so step 1 of `pnpm check` and of the Actions check |
| The allowlist of the lint | `apps/web/i18n-allowlist.json` |
| The pseudo-locale generator | `pnpm i18n:pseudo` (`packages/i18n/scripts/pseudo.mjs`, `packages/i18n/src/pseudo.ts`) |
| The tests | the package's vitest files (`pnpm test`, step 3 of `pnpm check`) and `bash tools/test/i18n.test.sh` (by hand: it builds `apps/web` and starts servers and a browser) |

Not covered yet, each a later row of the roadmap: a per-user locale, locale-aware dates, times and numbers in the
UI, RTL layout, Spanish. `apps/web` has two user-facing strings today, the name and the educational-use notice.

## Adding or changing a string

1. Add the message to `packages/i18n/messages/en.json`. The catalog is flat; an id is a dotted key that matches
   `^[a-z][A-Za-z0-9]*(\.[A-Za-z0-9]+)+$`, the screen or area first (`home.notice`, `app.name`).
2. Run `pnpm i18n:pseudo`: it rewrites `en-XA.json` from `en.json` (the same bytes when nothing changed).
3. Use it: `import { t } from "../i18n";` in `apps/web/src` (the relative path of `apps/web/src/i18n.ts`), then
   `t("home.notice")` or `t("course.members", { count, course })`.
4. Commit `en.json`, `en-XA.json` and the code together.

`pnpm check` needs no test edited for this: the package's vitest tests hold what stays true as the catalog grows
(the two files agree, every message parses, every id has the shape above), not what the catalog says today.
`tools/test/i18n.test.sh`, run by hand, does hold today's two messages as fixtures; a change of the catalog changes
its fixtures with it.

What catches a mistake, as the package's tests and `tools/test/i18n.test.sh` exercise it:

- An id that `en.json` does not hold is a type error (`MessageId` is `keyof typeof en`): `pnpm check` stops at
  typecheck.
- A message added to `en.json` without `pnpm i18n:pseudo` is a type error too (`en-XA.json` lacks the key:
  `Property '"<id>"' is missing`): `pnpm check` stops at typecheck.
- A message changed in `en.json` without `pnpm i18n:pseudo` (`en-XA.json` out of date), a message that does not
  parse, or an id of the wrong shape: a vitest test of the package fails, and `pnpm check` stops at test.
- A value the message names but the call does not pass is not a compile error (JSON carries no types for the
  message text): the formatter throws when the string is rendered.

## ICU MessageFormat

Messages are ICU MessageFormat, formatted by `intl-messageformat` (pinned in `packages/i18n/package.json`). One
example with a plural, `#` and a plain argument:

```
{count, plural, =0 {No members} one {# member} other {# members}} in {course}
```

With `course` = `CE 101` it gives `No members in CE 101`, `1 member in CE 101` and `1,234 members in CE 101` for
`count` 0, 1 and 1234. A plural or a select needs an `other` branch, or the message does not parse. An apostrophe
is text (`It's {name}'s turn`) unless it quotes a brace: `'{braces}'` prints `{braces}`. Do not build a sentence
from pieces in code; give the message its arguments.

## The string lint

`pnpm lint` runs `biome ci .` and then `node packages/i18n/lint/lint-strings.mjs`. The lint reads the `*.ts` and
`*.tsx` files under `apps/web/src` (not `*.d.ts`, not `*.test.*`) as syntax trees and reports strings in the
positions below. A string "has a letter" when it holds a Unicode letter; it "is prose" when it holds two words of
two letters or more separated by white space.

| Rule id | Reports |
|---|---|
| `jsx-text` | JSX text with a letter: `<p>Welcome back</p>` |
| `jsx-expression` | a string or template literal with a letter in a JSX child expression, also through `?:`, `&&`, `\|\|` and parentheses: `{late ? "Late" : null}` |
| `jsx-constant` | an identifier, in a JSX child or in a user-facing attribute, that the same file binds to a string literal with a letter; reported at the declaration |
| `jsx-attribute` | a string with a letter in `alt`, `title`, `placeholder`, `label`, `aria-label`, `aria-description`, `aria-placeholder`, `aria-roledescription` or `aria-valuetext` |
| `property` | a string with a letter as the value of an object property named `title`, `description`, `label`, `message`, `error`, `detail`, `summary`, `heading`, `placeholder` or `alt` (Next's `metadata`, the JSON body of a route handler) |
| `prose` | any other string or template literal that is prose |

Not reported: the first argument of `t(...)` or `x.t(...)` (the lookup itself); import and export specifiers;
directives (`"use client"`); type positions; a string compared with `===`, `!==`, `==` or `!=` and a `case` label;
the arguments of `console.*(...)` and of `new <Name>Error(...)` (text for developers); the other JSX attributes
(`className`, `data-*`, `lang`, `href`, ...), except inside a function written in one.

Output: one line per finding on stderr, `<path>:<line>:<column> <rule id> "<text>"` (white space collapsed, the
placeholders of a template literal shown as `{}`), then
`lint-strings: FAILED: <n> hard-coded user-facing string(s), <m> stale allowlist entr(ies); <k> files checked`.
When nothing is found: `lint-strings: ok, <k> files checked, <a> allowlisted` on stdout.

| Exit | Means |
|---|---|
| 0 | no finding outside the allowlist and no stale entry |
| 1 | a hard-coded string, or a stale allowlist entry |
| 2 | the lint could not run: an unknown flag, an unreadable source directory, or an allowlist that is unreadable or has an entry without `file`, `text` or a non-empty `reason` |

Flags, for the fixtures and for a look at another directory: `--src <dir>` (default `apps/web/src`) and
`--allow <file>` (default `apps/web/i18n-allowlist.json`). The lint's own unit test is
`packages/i18n/lint/lint-strings.test.mjs`, with one failing and one passing fixture under
`packages/i18n/lint/fixtures/`.

The fix for a finding is a catalog entry and `t("id")`. Where the string really is not for a user, the allowlist
is the way out; a wider exemption in the script changes this document with it.

## The allowlist

`apps/web/i18n-allowlist.json` ships empty:

```json
{ "allow": [] }
```

An entry names one string in one file, with the reason it stays out of the catalog:

```json
{
  "allow": [
    {
      "file": "src/app/api/v1/health/route.ts",
      "text": "the text exactly as the lint reports it",
      "reason": "why no user reads this string"
    }
  ]
}
```

- `file` is relative to the directory of the allowlist (`apps/web`), with forward slashes; `text` is the reported
  text, white space collapsed. An entry covers every occurrence of that text in that file.
- `reason` is required and may not be empty: exit 2 otherwise. An exception is right for a string in a
  user-facing position that no user reads (a protocol word a client matches on, a fixture value) and wrong for
  text that is merely waiting for its catalog entry.
- An entry that matches no finding any more is stale and fails the lint (exit 1, naming the entry), so the list
  cannot outlive the strings it excuses: remove the entry with the string.
- "Bridle" is not on the list: the name is the message `app.name` and is pseudo-localized like the notice.
  Whether the brand stays untranslated is a product question for a later card.

## The pseudo-locale

`en-XA` is `en` with every ASCII letter replaced by an accented look-alike, vowels written twice (longer text, as
a translation would be), and the whole message in brackets: `Bridle` becomes `[Ɓŕîîðļéé]`. Arguments, `#`, plural
and select keywords, number and date skeletons and tag names are kept, so a pseudo message formats like its
source.

The locale is fixed at build time by `NEXT_PUBLIC_LOCALE`: `en` when it is unset or empty, `en-XA` for the
pseudo-locale; another value throws (`unknown locale "fr"`), so a typo fails the build. Next inlines the variable,
so one build is one locale and `next start` serves the locale of its build. The health route has no user-facing
string and answers the same body in both locales.

```sh
NEXT_PUBLIC_LOCALE=en-XA pnpm --filter web build   # then: pnpm --filter web start
NEXT_PUBLIC_LOCALE=en-XA pnpm e2e:smoke            # the smoke test against a dev server in the pseudo-locale
rm -rf apps/web/.next                              # after an en-XA build, so a later `next start` is en again
```

The smoke test reads the strings it expects from the catalog of the locale, asserts `<html lang="en-XA">` first,
and writes `.bridle/screenshots/smoke-home-en-XA.png`. What to look for on a pseudo-locale page:

- a message without its closing or opening bracket is truncated or clipped by the layout;
- plain English is a string that did not come from the catalog;
- text that overflows its box at this length will overflow in a longer language.

## Limits

The lint is a syntax heuristic without type information. Known gaps:

- a string constant imported from another file and rendered in JSX is not followed (`jsx-constant` looks at the
  same file only);
- a single word outside JSX and outside the property names above passes (`prose` needs two words);
- strings that reach the page from outside `apps/web/src` (another package, the database) are not scanned.

The pseudo-locale smoke and a look at the `en-XA` page are the backstop for what the lint does not see.
