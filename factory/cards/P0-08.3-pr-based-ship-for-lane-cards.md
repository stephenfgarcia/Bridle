# P0-08.3 PR-based ship for lane cards

## Spec

What: a lane card ships through a pull request. Why: the P0-08 row: "PR-based ship (rebase on origin/main, `pnpm check`, push, `gh pr create`, merge when Actions is green, merge commit in `## Ship`)"; the owner's decision of 2026-11-17: merges stay serial, each rebased and green.
Acceptance criteria:
1. `tools/factory/ship.sh <id>` run in a lane's worktree: refuses on a dirty tree, on a branch that is not `lane/<name>`, on a failing `tools/factory/lane-check.sh`, on an open manual gate (P0-08.1) and when `## Test` does not start with `RESULT: PASS` or `## Review` with `VERDICT: PASS`; otherwise fetches, rebases the branch on `origin/main` (stopping with the conflict list if the rebase does not apply; lock files are regenerated, never hand-merged), runs `pnpm check`, pushes the branch, opens a pull request titled `<id>: <title>` with the attribution line, waits for the required `check`, merges with a merge commit only when it is green and prints the merge commit and the Actions run URL. A `--dry-run` prints each step without pushing or opening anything.
2. Serial merges: `ship.sh` refuses to merge while another lane's pull request is being merged (a lock held in the main checkout's `.bridle/`, released on exit, with a stale-lock rule stated in the header), and re-checks that the branch still contains `origin/main` just before merging.
3. The `Cards: <id> shipped` step for a lane card is defined and scripted or documented in the script's header: where `## Ship`, the done state, the board, the log entry and the in-flight paragraphs of `docs/plan/progress.md` are written (on `main`, by the foreman of the main checkout, after the merge) so that two lanes never edit `docs/plan/progress.md` at once.
4. Proof: this card itself ships through `tools/factory/ship.sh` from a lane worktree, as one real pull request on github.com/stephenfgarcia/Bridle that is merged green; `## Ship` holds the pull request URL, the merge commit and the run URL. `tools/test/ship.test.sh` (with "card P0-08.3" in its second line) proves the refusals and the dry run against a local bare remote, with `gh` stubbed, and makes no network call.
Files: `tools/factory/ship.sh`, `tools/test/ship.test.sh`, `docs/ops/github.md` (the pull-request path beside the direct push), `.claude/settings.json` only if a command the script runs is not allowed yet (say which).

Out of scope for every P0-08 sub-card: product code (`apps`, `packages`, `crates`), `tools/agent-hq/`, and the monitor's page and viewer beyond what an acceptance criterion names. Process notes from 2026-11-17 that apply here: an absolute claim ("every", "all", "none", "only") in a shipped document or comment needs a test or a command that holds it; a station's verdict is FAIL only for an unmet acceptance criterion, a failing command, a false statement in a shipped file or a real defect, and everything else is an advisory; negative proofs and experiments run in a scratch copy or behind a backup checked with `cmp`.
