# PX-01.1 Model types and validation

## Spec

Pitch card S1 of `docs/plan/pitch-plan.md` (core lane; packages/model and packages/solver), approved by the owner with the plan on 2026-11-18. What: Model types and validation: nodes, members, sections, materials, supports, loads, load cases; JSON format. Why: the showcase of 2026-12-16 for the owner's pitch and thesis defense on 2027-01-01. Review station: no (the pitch process: one agent builds and tests; `pnpm check` green before the commit). The foreman writes this card's acceptance criteria here before its build starts.

Acceptance criteria (foreman, 2026-11-18):
1. A new workspace package `packages/model` (name `@bridle/model`, TypeScript, built and tested the way `packages/i18n` is) exports the types of a structural model: `Node` (id, x, y, z), `Member` (id, start node, end node, section id, material id, kind `frame` or `truss`, roll angle, end releases), `Section` (id, name, A, Iy, Iz, J, and the depths the stress check needs), `Material` (id, name, E, G, fy, density), `Support` (node id, six restraint flags), `NodalLoad`, `MemberUniformLoad` and `MemberPointLoad` (each with a load case id and a global or local direction), `LoadCase`, and `Model` (a `version`, `units`, and the lists above).
2. Conventions, stated in the package's README and in the type comments: the global Z axis is up and gravity acts along minus Z; the model stores forces in kN and lengths in m (so moments are kN·m and E is kN/m²); the documents name which display units the interface uses (MPa for stress, mm for deflection), with the conversions taken from `packages/units` where it has them.
3. `validateModel(model)` returns a list of issues, each with a code, a message key and the ids it concerns, and returns an empty list for a valid model. It reports at least: a duplicate id, a member that names a missing node, section or material, a member of zero length, a non-positive A, I, J, E or G, a support or load that names a missing node, member or load case, a point load position outside the member, and a model with no support.
4. `parseModel(json)` and `serializeModel(model)` round-trip: a serialized model parses to an equal model, and a JSON text of the wrong shape is refused with an issue list instead of an exception.
5. Three fixture models are exported for later cards and tests: a simply supported beam, a portal frame and a small truss, each valid by criterion 3.
6. Unit tests cover each issue code of criterion 3 with one failing model, the round trip, and the three fixtures; `pnpm check` is 7/7; `factory/lanes.json` already gives `packages/model/` to core.
Files: `packages/model/` (new), `pnpm-lock.yaml` and the workspace files only as a new package needs. Out of scope: any analysis (S2 onwards), any user interface, load combinations.

Acceptance criteria:
1. Types: in `src/types.ts`, exported from the package.
2. Conventions: the README ("Conventions") and the header and field comments of `src/types.ts` and `src/geometry.ts`.
   Display units: MPa and mm. The m to mm factor is named from `packages/units` (`LENGTH_IN_METRES.mm`);
   `packages/units` has no stress conversion, so the README states 1 MPa = 1000 kN/m² itself. The package converts
   nothing and does not import `packages/units`.
3. `validateModel`: codes `duplicate-id`, `duplicate-support`, `missing-node`, `missing-section`, `missing-material`,
   `missing-member`, `missing-load-case`, `zero-length-member`, `non-positive-value`, `load-position-outside-member`,
   `no-support`.
4. `parseModel` returns `{ ok: true, model } | { ok: false, issues }` with the codes `invalid-json`, `invalid-shape`,
   `unsupported-version`, `unsupported-units`; `serializeModel` writes two-space JSON with keys in a fixed order.
5. Fixtures: three functions, each returning a new model (so a caller can change one without changing the next).
6. Tests: see `## Test`.

Decisions and their reasons:
- Message keys are `model.issue.<code>` (a template type over the code union). No catalog entry was added; the card
  that first shows an issue on screen has to add the 15 keys to `packages/i18n/messages/en.json`.
- `ModelIssue.path` (for example `sections[0].A`) is an addition to "code, message key, ids": `non-positive-value`
  and `invalid-shape` need it to say which field.
- Member local axes (README and `src/geometry.ts`): local x from start to end node; roll 0 and not vertical: local y
  horizontal along (global Z) × (local x), local z = (local x) × (local y), upward; vertical: local y = global +Y,
  local z = global -X for a member running upward and +X for one running downward; the roll angle (`rollAngleDeg`,
  degrees) rotates local y and z about local x by the right-hand rule. With this, every member of the portal frame
  fixture (X-Z plane, columns upward, beam along +X) has local y = global +Y and bends in plane about local y (`Iy`).
- `memberLocalAxes` is code, not only a comment, so that the convention is tested and S2 can call it. It is geometry,
  not analysis.
- The roll angle is stored in degrees and named `rollAngleDeg`; density is in kg/m³ (the spec names kN and m only).
- `Section` depths: `depthY` and `depthZ`, the overall dimensions along local y and z; the comments say the stress
  check takes the extreme fibre at half of them (a section symmetric about its axes).
- End releases are rotational only (`rx`, `ry`, `rz` per end, local axes). Translational releases are not in the type.
- Loads have an `id` (the interface needs one to edit or delete a load). Ids are unique per list, and the three load
  lists are three lists.
- `parseModel` checks the shape only and does not run `validateModel`, so a model in progress can be saved and
  loaded. It refuses keys the format does not have rather than dropping them.
- `serializeModel` throws on a value that is not of the format's shape (a NaN coordinate, say), since the JSON would
  not parse back to an equal model.
- `validateModel` also reports a non-positive `depthY`, `depthZ` or `fy`, and a second support on one node
  (`duplicate-support`); the spec says "at least". It does not check `density`.
- Fixture names are short codes (`I 300x150`, `S355`, `LC1`), not text to translate. The section values are round
  illustrative numbers, not from a section table.

Deviations from the Spec and the foreman's notes:
- `NodalLoad` has six global components (`fx`, `fy`, `fz`, `mx`, `my`, `mz`) and no direction field: a node has no
  local axes, so its direction is always global. `MemberUniformLoad` and `MemberPointLoad` have `axes: "global" |
  "local"` and `direction: "x" | "y" | "z"`.
- The fixtures are functions, not constants.

For the next cards:
- S2: build the transformation from `memberLocalAxes(start, end, member.rollAngleDeg)`; it returns `undefined` for a
  zero-length member.
- S4: a uniform load is per unit of the member's own length, also with a global direction on an inclined member.
- S5: `planarTruss()` restrains `uy` at all five nodes and no rotation; nodes joined only by truss members have no
  rotational stiffness, which the solver has to handle. `validateModel` does not check stability.
- Not run in this card: `tools/test/workspace.test.sh` and `tools/test/image.test.sh` (not in this card's list).
