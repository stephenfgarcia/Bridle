# PX-01.9 Web Worker wrapper and speed test

## Spec

Pitch card S9 of `docs/plan/pitch-plan.md` (core lane; packages/model and packages/solver), approved by the owner with the plan on 2026-11-18. What: Web Worker wrapper and a speed test (200 members solved in under 100 ms on the development machine). Why: the showcase of 2026-12-16 for the owner's pitch and thesis defense on 2027-01-01. Review station: no (the pitch process: one agent builds and tests; `pnpm check` green before the commit). The foreman writes this card's acceptance criteria here before its build starts.

Acceptance criteria (foreman, 2026-11-18):
1. Message protocol: `packages/solver` defines typed request and response messages for running `solve` off the main thread (a request with an id and a model; a response with the same id and the result of `solve`, or a typed error when `solve` throws), and a pure function that handles one request and returns the response together with the list of buffers to transfer (the `Float64Array`s of the result). It is tested without a worker.
2. Worker entry: a module (exported as `@bridle/solver/worker`) that wires that function to `self.onmessage` and `postMessage`, usable from a browser module worker and written so that the bundler of `apps/web` (Next.js) can load it with `new Worker(new URL(...), { type: "module" })`. The README shows that line. It imports nothing that needs the DOM or Node.
3. Client: `createSolverClient(makeWorker)` returns an object with `solve(model)`, which returns a promise of the result, and `dispose()`. Latest wins: when a newer `solve` call is made before an older one has answered, the older promise settles with a typed `superseded` outcome and its late answer is ignored. A worker error or a typed error response rejects or settles the pending call with a typed failure, and the client can be used again afterwards (it makes a new worker). The client is tested with a fake worker object (messages delivered by the test), including the superseded case, the error case and `dispose`.
4. One test runs the real handler across a real thread boundary in Node (`node:worker_threads` or the test runner's worker support) with the portal frame fixture and compares the result with a direct `solve` call, to prove that the result survives the transfer.
5. Speed: a script `pnpm --filter @bridle/solver bench` prints the median time of `solve` for a 3D frame of about 200 members, one of about 400 members, a 200-element cantilever along an axis and one along a skew direction, each with the number of nodes and the smallest pivot ratio. The card's Test section records the numbers measured on the development machine. A unit test asserts only a loose bound that cannot flake on a slow CI machine (the 200-member frame under 2 seconds); the README states the measured numbers as measurements of one machine on one date, and says that the cost grows steeply with the number of free degrees of freedom.
6. If the 200-member frame takes more than 100 ms on the development machine, say so plainly in the card and the README; do not change the factorization in this card.
7. `pnpm check` is 7/7 and `bash tools/test/lanes.test.sh` passes.
Files: `packages/solver/`. Out of scope: creating the worker in `apps/web` and wiring it to the store (W8), any change to `solve`, the factorization or the element.

### Decisions

1. **Latest wins: the worker is left to finish; it is not terminated.** A newer `solve` call resolves the older promise at
   once with `{ status: "superseded" }`. The request of the older call stays with the worker and its answer is dropped. The
   client does not post the newer model while the worker is busy: it keeps only the newest call and posts it when the worker
   answers. So the worker computes at most one request nobody waits for, however many calls arrive meanwhile (a test makes 50
   calls and checks that only request 1 and request 50 are posted). Why not terminate: a new worker must load and compile the
   solver before it can start, at every superseded call, while the solves measured below have medians of 7 to 76 ms, so waiting
   costs at most one such solve. The start time of a worker in a browser was not measured. Not covered: a `solve` that never
   returns blocks the worker; the client has no timeout.
2. **The promise of `solve` never rejects.** It resolves with a `SolveOutcome`: `solved` (with the result, which may be a
   refusal `ok: false`), `superseded`, `failed` (with `failure.kind`: `solve-threw`, `worker-error`, `not-sent`) or `disposed`.
   The criterion allows "rejects or settles"; settling leaves no unhandled rejection for a superseded call.
3. **Worker replacement.** `onerror` and `onmessageerror` end the worker: handlers set to `null`, `terminate()`, and the next
   call makes a new one with `makeWorker`. If the error comes while the worker computes a superseded request, the newest call
   is not failed; it is posted to a new worker at once. A `solve-error` response and a `postMessage` that throws keep the worker.
   A `makeWorker` that throws gives `worker-error`, and the next call tries again.
4. **No listeners to leak.** The client sets the three handler properties of the worker and nothing else (no
   `addEventListener`); it holds one worker at most; `dispose()` terminates it, and later `solve` calls resolve as `disposed`
   without making a worker.
5. **`@bridle/solver/client` as a separate export.** `client.ts` imports types and one guard, so the main thread's bundle
   does not need the solver's code. The client is also exported from `@bridle/solver`.
6. **`SolverWorker` is a structural interface** (`postMessage`, `terminate`, three handler properties) so that a test can pass
   a plain object. That a DOM `Worker` fits is checked by the type check of `src/client.test.ts` (I confirmed the check is
   real: adding a method to the interface gave type errors).
7. **Node cannot run the package's TypeScript source** (imports without extensions), so the bench script and the thread test
   bundle with Vite first. The thread test runs the bundled `src/worker.ts` itself in a `node:worker_threads` worker, with six
   lines of glue for `self`, `postMessage` and the delivery of messages, and also asserts that the bundle has no `import` and
   no `require`.

### Deviations and things to know

- **Generators.** The foreman's note said to reuse the generators of the tests, moved to a shared file. I wrote new ones in
  `src/bench.ts` and left `tower`, `onLine` and `chain` in `src/solve.test.ts` where they are: they build on that file's
  `frame` helper and `tower` returns a model without supports or loads, and moving them would have meant editing the test
  file of cards S3 and S4. The new ones are tested in `src/bench.test.ts` (validity, sizes, equilibrium, a closed form).
- **Not verified in Next.js.** `apps/web` is out of scope, so no worker was created in a browser or by the bundler of
  Next. The README says so and gives a fallback (a one-line local file that imports `@bridle/solver/worker`, loaded by a
  relative URL). W8 must also add `@bridle/solver` to the dependencies of `apps/web` and to `transpilePackages`.
- **Criterion 6 does not apply:** the 200-member frame took 6.9 ms (median), under 100 ms. The skew cantilever of 200
  elements took 76.1 ms, inside the target but with little room; nothing larger was measured.
- `src/worker.test.ts` and `bench/run.mjs` import `vite`. The type check of this package resolves the `node:` imports of
  the test although the package has no `@types/node` dependency of its own; I take it that Vite's type declarations bring
  the Node types in, and did not check further. The bundle test checks the worker entry for `import`, `require`,
  `document.`, `window.` and `process.`.
- The times are of `solve` alone; the cost of copying the model to the worker and the result back was not measured.
- The frontmatter of this card was not touched.

    // apps/web/package.json: add "@bridle/solver": "workspace:*"; next.config.mjs: add "@bridle/solver" to transpilePackages
    import { createSolverClient } from "@bridle/solver/client";
    const client = createSolverClient(
      () => new Worker(new URL("@bridle/solver/worker", import.meta.url), { type: "module" }),
    );
    const outcome = await client.solve(model);   // never rejects
    // outcome.status: "solved" (outcome.result, check result.ok) | "superseded" | "failed" (outcome.failure) | "disposed"
    client.dispose();                             // on unmount

Create the client in the browser only (in an effect or an event handler): `makeWorker` runs at the first `solve` call.
