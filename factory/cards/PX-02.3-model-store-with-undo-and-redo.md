# PX-02.3 Model store with undo and redo

## Spec

Pitch card W3 of `docs/plan/pitch-plan.md` (web lane; apps/web), approved by the owner with the plan on 2026-11-18. What: Model store with undo and redo. Why: the showcase of 2026-12-16 for the owner's pitch and thesis defense on 2027-01-01. Review station: no (the pitch process: one agent builds and tests; `pnpm check` green before the commit). The foreman writes this card's acceptance criteria here before its build starts.

Acceptance criteria (foreman, 2026-11-18):
1. The workspace's model lives in one store (zustand). Its commands are pure functions of (model, arguments) to a new model, kept in a file that imports neither React nor zustand: add, move and delete a node (deleting a node also deletes the members, the support and the loads on it); add and delete a member (deleting a member also deletes its loads); update a member's section, material, kind, roll angle and end releases; set and remove a node's support; add, update and remove a nodal load, a member uniform load and a member point load; add a section, a material and a load case; replace the whole model. A command that changes nothing returns the same model object.
2. New ids: a new node, member, support or load gets the next free id of its kind (for example `n5` after `n4`), never one in use.
3. Undo and redo: every command that changes the model is one undo step; undo and redo walk a history with a stated limit (at least 100 steps); a new command after an undo discards the redo steps; replacing the whole model clears the history. The store exposes whether undo and redo are possible.
4. Interface: Undo and Redo buttons in the workspace (disabled when not possible) and the keyboard shortcuts Ctrl or Cmd with Z, and Ctrl or Cmd with Shift and Z or Ctrl with Y, active on `/workspace` except while the focus is in a text field.
5. The store exposes the issues of `validateModel` for the current model, recomputed only when the model changes. The side panel shows "No issues" or the number of issues and their list, each with a readable message from the catalog (the message keys of `packages/model`, including the finite-number check if `main` has it by then) and the ids concerned.
6. `/workspace` draws the store's model; the example-model switch replaces the model in the store; the camera re-frames only when the whole model is replaced, not on an edit.
7. Tests: unit tests of each command of criterion 1 (among them the cascades of the two deletes, and "no change returns the same object"), of the ids, and of undo, redo, the discarded redo steps, the cleared history and the limit; the smoke test checks that Undo and Redo are present and disabled on a fresh `/workspace` and that the issues area says there are none for the portal frame. `pnpm check` is 7/7; `tools/test/web.test.sh` and `tools/test/i18n.test.sh` are kept passing.
8. Every user-facing string is in the catalog of `packages/i18n`.
Files: `apps/web/`, `e2e/`, `packages/i18n/messages/`, `tools/test/web.test.sh`, `tools/test/i18n.test.sh`, `pnpm-lock.yaml` only if needed. Out of scope: the drawing and editing tools that call these commands (W4 to W7), saving to a file or server (W12), analysis (W8).

## Build

What was built, in three layers under `apps/web/src/components/model/`, and the interface on top:

1. `commands.ts`: the pure commands `(model, args) => model`. It imports `@bridle/model` only (no React, no zustand). A command that changes something returns a new `Model` in which only the changed lists are new arrays and only the changed entries new objects; a command that changes nothing, or that refuses its arguments, returns the model object it was given. No command throws on the refusals listed below.
2. `history.ts`: the pure history `{ past, present, future }` with `createHistory`, `record` (one undo step, drops the redo steps, keeps at most `limit` steps and drops the oldest), `undo`, `redo`, `canUndo`, `canRedo`. `HISTORY_LIMIT` is 200 undo steps. No middleware dependency was added.
3. `modelStore.ts`: the zustand store `useModelStore` (state `history`, `source`, `loadCount`; one action per command, `apply`, `undo`, `redo`, `replaceModel`) and the selectors `selectModel`, `selectCanUndo`, `selectCanRedo`, `selectFrameKey`, `selectIssues`. It starts with the portal frame. `createModelState(initial, source, limit?)` makes the same state for a store of a test.
4. `shortcuts.ts`: `historyShortcut`, `isTextField`, `handleHistoryKey`, pure functions of the fields of a key event. `issueMessages.ts`: the catalog id of each issue code.
5. Interface: `HistoryControls.tsx` (Undo and Redo, a segmented pair in the top right corner of the viewport area, in the style of the view buttons, disabled while the store has no step); `WorkspaceView.tsx` reads the model, the issues and the frame key from the store, attaches the shortcuts to the window while it is mounted, and its example switch calls `replaceModel`; `SidePanel.tsx` shows, under the counts, "Issues" with "No issues" or the number of issues and one entry per issue: the catalog message, the ids, and the issue's `path` where it has one.

By acceptance criterion:

1. The commands, all exported from `commands.ts` (ids are strings; lengths in m, forces in kN, as in `@bridle/model`):
   - `addNode(model, { x, y, z })`
   - `moveNode(model, { id, x, y, z })`
   - `deleteNode(model, { id })`: also deletes the members that start or end at the node with their uniform and point loads, the node's support and its nodal loads.
   - `addMember(model, { startNodeId, endNodeId, sectionId?, materialId?, kind?, rollAngleDeg?, releases? })`: defaults are the model's first section, its first material, `frame`, 0, nothing released.
   - `deleteMember(model, { id })`: also deletes the member's uniform and point loads; its nodes stay.
   - `updateMember(model, { id, sectionId?, materialId?, kind?, rollAngleDeg?, releases? })`: `releases` is `{ start?: Partial<MemberEndRelease>, end?: Partial<MemberEndRelease> }`; what is left out keeps its value.
   - `setSupport(model, { nodeId, ux, uy, uz, rx, ry, rz })`: adds the support or replaces the node's; six `false` remove it.
   - `removeSupport(model, { nodeId })`
   - `addNodalLoad(model, { nodeId, loadCaseId?, fx?, fy?, fz?, mx?, my?, mz? })`: defaults are the first load case and 0.
   - `updateNodalLoad(model, { id, nodeId?, loadCaseId?, fx?, fy?, fz?, mx?, my?, mz? })`, `removeNodalLoad(model, { id })`
   - `addMemberUniformLoad(model, { memberId, value, loadCaseId?, axes?, direction? })`: defaults are the first load case, `global`, `z`.
   - `updateMemberUniformLoad(model, { id, memberId?, loadCaseId?, axes?, direction?, value? })`, `removeMemberUniformLoad(model, { id })`
   - `addMemberPointLoad(model, { memberId, value, position, loadCaseId?, axes?, direction? })`: the same defaults.
   - `updateMemberPointLoad(model, { id, memberId?, loadCaseId?, axes?, direction?, value?, position? })`, `removeMemberPointLoad(model, { id })`
   - `addSection(model, { name, A, Iy, Iz, J, depthY, depthZ })`, `addMaterial(model, { name, E, G, fy, density })`, `addLoadCase(model, { name })`
   - `replaceModel(model, { model: next })`: returns `next`.
   - The argument types are exported beside them (`AddNodeArgs`, `UpdateMemberArgs`, `MemberReleasesPatch`, ...).

   Refusals (each returns the same model object):
   - every command that takes an id: an id its list does not hold (`moveNode`, `deleteNode`, `deleteMember`, `updateMember`, the three `update...Load` and three `remove...Load`); `removeSupport` on a node without a support; `setSupport` on a node id that is not a node;
   - a number that is not finite: a coordinate (`addNode`, `moveNode`), a roll angle, a load component, value or position;
   - `addMember`: the same node at both ends; an end that is not a node; two nodes closer than `ZERO_LENGTH_TOLERANCE`; a member that already joins the two nodes, in either direction; a section or material that is not in the model, or left out while the model has none; a kind other than `frame` and `truss`;
   - `updateMember`: a section or material that is not in the model; a kind other than `frame` and `truss`. One refused part refuses the whole update (the same for the load updates);
   - the load commands: a node, member or load case that is not in the model, or a load case left out while the model has none; axes other than `global` and `local`; a direction other than `x`, `y`, `z`; for a point load, a position below 0 or beyond the member's length by more than `POSITION_TOLERANCE` (on add, and on an update that gives the member or the position; not checked when a node of the member is missing);
   - `addSection`: `A`, `Iy`, `Iz`, `J`, `depthY` or `depthZ` that is not a finite number above zero; `addMaterial`: `E`, `G` or `fy` that is not a finite number above zero, a density that is not finite or is below zero;
   - an update or a move to the values the entry already has.

   Not refused, so `validateModel` reports it afterwards: `addNode` at the place of another node; `moveNode` that gives a member zero length or leaves a point load beyond its member; a nodal load whose six components are 0. `addLoadCase` refuses nothing and names are not checked.
2. Ids: `nextId(list, prefix)` gives the prefix and one more than the largest number after that prefix in the list, and steps on while the result is taken, so it is not an id of the list. Prefixes (`ID_PREFIX`): `n` nodes, `m` members, `s` sections, `mat` materials, `lc` load cases, `nl` nodal loads, `ul` member uniform loads, `pl` member point loads. `nextNodeId(model)`, `nextMemberId(model)` and the six others name the id the next add would give. A support has no id. In the portal frame, whose members are `c1`, `b1`, `c2`, the first added member is `m1`.
3. Undo and redo: each store action that changes the model is one undo step (`record`); a refused command records nothing and leaves the store's state object as it was, so no subscriber is told. The limit is `HISTORY_LIMIT` = 200 undo steps. A command after an undo drops the redo steps. `replaceModel(model, source?)` of the store starts a new history (no undo, no redo) and adds one to `loadCount`. `selectCanUndo` and `selectCanRedo` say whether a step exists. Undo and redo bring back the earlier model objects themselves, not copies.
4. Undo and Redo buttons as above. Shortcuts, on `/workspace` while `WorkspaceView` is mounted: Ctrl or Cmd with Z is undo; Ctrl or Cmd with Shift and Z, or Ctrl with Y, is redo; nothing with Alt. A key pressed while the target is a `<textarea>`, an `<input>` of a type that holds text, or an editable element is left to the browser. A handled key calls `preventDefault`.
5. `issuesOf(model)` runs `validateModel` once per model object (a `WeakMap` keyed on the object) and `selectIssues` is that for the present model: the same array comes back until the model object changes, and again when an undo brings an earlier object back. The catalog holds a message for each of the 15 codes of `@bridle/model` (the 11 of `validateModel`, the 4 of `parseModel`; `main` has no finite-number code at this time).
6. `/workspace` draws `selectModel`; the example switch calls `replaceModel(fixture, id)` after clearing the hover and the selection; the viewport's `frameKey` is `selectFrameKey` (the text of `loadCount`), which a command, an undo and a redo do not change.
