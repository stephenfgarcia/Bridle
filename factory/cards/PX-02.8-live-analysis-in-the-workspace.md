# PX-02.8 Live analysis in the workspace

## Spec

Pitch card W8 of `docs/plan/pitch-plan.md` (web lane; apps/web), approved by the owner with the plan on 2026-11-18. What: Live analysis: the worker wired to the store, status and the unstable-model message. Why: the showcase of 2026-12-16 for the owner's pitch and thesis defense on 2027-01-01. Review station: no (the pitch process: one agent builds and tests; `pnpm check` green before the commit). The foreman writes this card's acceptance criteria here before its build starts.

Acceptance criteria (foreman, 2026-11-18):
1. `apps/web` depends on `@bridle/solver` (`workspace:*`, added to `transpilePackages`), and creates the solver worker in the browser with the client of card S9 (`createSolverClient` from `@bridle/solver/client`, the worker entry `@bridle/solver/worker`; if the bundler does not resolve the package name inside `new URL(...)`, a one-line local worker file that imports it, as S9's card describes). The production build succeeds and the worker loads in the built app.
2. Live analysis: whenever the store's model changes and has no issues of `validateModel`, the model is sent to the worker (latest wins); the result is kept in an analysis store keyed to the model object it belongs to, so that a result is never shown against a newer model. While a solve is pending the previous result stays visible but marked as stale.
3. Status: a compact status area in the workspace shows one of: "Analysed" with the solve time in ms; "Analysing…"; "Fix the issues first" with the number of issues, when `validateModel` reports any; "Unstable" with the node and the direction that the solver names, in words ("free to move along X at node n3", "free to rotate about Y at node n2"), a one-line hint, and, when the model lies in one X-Z plane and has no out-of-plane restraints, a button that runs "Restrain out of plane"; "Not supported yet" naming the feature and the members (truss members, releases) when the solver refuses for that reason; "Analysis failed" for a worker failure, with a Retry button. A warning line appears when the result's smallest pivot ratio is below 1e-9, saying that the result may have lost accuracy.
4. A first, plain results view in the side panel (a "Results" section, shown when a result exists), for the active load case: the reactions at each support (six components with units, kN and kN·m, values of negligible size shown as 0), the displacements of the selected node (mm for translations, rad for rotations), and for the selected member its end forces at the start and the end. Numbers use a sensible fixed number of significant digits and the units of the owner's answers (kN, kN·m, mm).
5. The example models analyse on opening: the portal frame shows "Analysed" and its reactions; switching the example, undo and redo all trigger a new analysis and the display follows.
6. Tests: unit tests of the pure parts (the mapping from a solve result or refusal to the status shown, the wording for each degree of freedom, the formatting of numbers and units, the store logic that discards a result for an older model); a browser test that opens `/workspace`, waits for "Analysed" on the portal frame, reads the horizontal reactions and checks that they sum to the applied lateral load within rounding, then deletes a support and sees the status change to unstable or to the issue state; `pnpm check` is 7/7; `pnpm --filter web build` succeeds; `tools/test/web.test.sh` and `tools/test/i18n.test.sh` are kept passing. One screenshot at 1280 by 720 for the foreman: the portal frame analysed with the Results section visible.
7. Every user-facing string is in the catalog of `packages/i18n`.
Files: `apps/web/`, `e2e/`, `packages/i18n/messages/`, `pnpm-lock.yaml`, `tools/test/web.test.sh`, `tools/test/i18n.test.sh`, `docs/ops/local-dev.md` if a sentence there becomes untrue. Out of scope: the deflected shape and reaction arrows in the viewport (W9), diagrams (W10), utilization (W11).

What was built, in layers. Everything new is under `apps/web/src/components/analysis/`. The pure parts import no React, no zustand and no worker: `analysisState.ts` (the state of the analysis and its reducer), `status.ts` (from that state to the status shown), `format.ts` (how a number is written), `results.ts` (from a load case's result to the printed values), `runAnalysis.ts` (the wiring between a source of models, a solver client and the reducer). `analysisStore.ts` is the zustand store, `solverWorker.ts` makes the worker, `LiveAnalysis.tsx` runs the wiring while the workspace is mounted, `AnalysisStatus.tsx` and `ResultsPanel.tsx` render.

The worker is made by `makeSolverWorker` in `solverWorker.ts` with the line of card S9, `new Worker(new URL("@bridle/solver/worker", import.meta.url), { type: "module" })`, and given to `createSolverClient` from `@bridle/solver/client`. 2. Live analysis: `LiveAnalysis` (mounted by `WorkspaceView`, so on `/workspace` only) subscribes to the model store once. Each new model object is looked at: with issues of `validateModel` (`issuesOf`) it is not sent (event `blocked`); otherwise it is sent with `client.solve` (event `requested`) and the outcome becomes `solved`, `failed` or `superseded`. Latest wins twice: the solver's client posts only the newest waiting model, and the reducer drops a `solved` or `failed` whose model object is not the state's model. The answer is kept with the model object it was computed for (`Answer.model`). `shownResults(state, model)` gives the results for the model on screen: fresh when they were computed for that object; stale, only while the answer for that object is awaited; nothing otherwise. The Results section shows stale values at half opacity under the line "Updating. These values belong to the model before the last change." The status and the Results section both take the model on screen from the model store and compare it with the answer's model themselves, so they do not depend on the analysis store having caught up.
3. Status: `AnalysisStatus` at the top of the side panel, where it stays while the panel scrolls (`position: sticky`). One of: "Analysing…"; "Analysed" with the time in ms; "Fix the issues first" with the number of issues; "Unstable" with the sentence for the degree of freedom the solver names ("The structure is unstable. The analysis stopped where it found the structure free to move along X at node n3." and the five others: move along Y or Z, rotate about X, Y or Z), the hint "That node is where the check stopped, not always the cause. Look for a missing support or restraint, or for a part that is not connected to the rest.", and, when "Restrain out of plane" would add a restraint, a line and the button; "Not supported yet" with "Truss members are not analysed yet: t1, t2, ..." and "Members with end releases are not analysed yet: ..." (the first eight ids, then "and N more"); "Analysis failed" with a sentence for the kind of failure, the technical text of the failure and a Retry button; and "Not analysed" for the solver's `non-finite` refusal (not in the criterion, added so that no outcome of the solver is silent). A warning line appears under "Analysed" when `smallestPivotRatio` is below 1e-9 (`PIVOT_WARNING`), with the ratio.
4. Results: a "Results" section in the side panel after Loads, rendered only while `shownResults` gives results. For the active load case (`activeLoadCaseId(model, loadCaseId of the tool store)`): one card per support with Fx, Fy, Fz in kN and Mx, My, Mz in kN·m in global axes, and a card "Sum of the reaction forces" (Fx, Fy, Fz); with a node selected, its displacement (ux, uy, uz in mm, rx, ry, rz in rad); with a member selected, its end forces at the start and at the end, under a note that says they are the forces and moments the joints apply to the member's ends in its local axes and not values of an internal force diagram. Numbers: `formatNumber`, four significant digits; a value at most 1e-9 of the largest value of its group prints as "0" (the groups: reaction forces, reaction moments, translations, rotations, member end forces, member end moments, each over the whole load case); plain decimals from 0.001 to below 1 000 000, an exponent outside.
5. The examples analyse on opening: the portal frame shows "Analysed" and its reactions (Fx -10.04 and -9.962 kN, sum -20.00 kN); the beam shows "Analysed"; the truss shows "Not supported yet" with its seven members, because the solver has no truss members yet (card S5). Switching the example, undo and redo each give a new model object and so a new analysis; the smoke test follows all three.

How the worker is created and disposed: `LiveAnalysis` has one effect. Each run of it calls `createSolverClient(makeSolverWorker)` and `startLiveAnalysis`; the client makes the worker at the first model it sends, so a page whose model has issues makes none. The cleanup stops the wiring, calls `client.dispose()` (which terminates the worker), clears the Retry handler and resets the analysis store. When React's strict mode runs the effect, cleans it up and runs it again in development, the second run has a client of its own, so nothing uses a disposed client. Decisions:
- The status area is at the top of the side panel, not over the viewport. A first version sat under the Undo and Redo buttons; its "Unstable" box covered the top right node of the portal frame in the Front view and took the pointer from the tools (smoke test 6 failed on it), so it was moved.
- The time shown is measured on the main thread, from sending the model to receiving the answer: it includes copying the model and the result, waiting for a solve already in progress and, for the first analysis after the page opens, starting the worker (9 to 24 ms for the first analysis of the portal frame in the runs looked at here; 115 and 580 ms were seen in `next dev` when the worker's code was compiled on demand). The solver reports no time of its own. The tooltip of the number says what it is.
- No result is kept per model object beyond the last answer: undo and redo send the earlier model object again and its result arrives a few ms later. Card PX-02.3's note allows a cache per model object; it was not needed for the criteria.
- When the model has issues, or the call failed, no earlier result is shown at all (the reducer drops the answer). Stale values are shown only while an answer is awaited.
- "Restrain out of plane" is offered in the "Unstable" status when `restrainOutOfPlane(model).outcome === "done"`, that is, when all nodes share one Y and at least one node lacks uy, rx or rz. The criterion says "has no out-of-plane restraints"; that literal rule would hide the button for a frame on two pinned bases (a pin restrains uy), which is the case that needs it. The line above the button says "this may be the cause", because the button is also offered when the instability is in the plane.
- The wording for an unstable model says where the analysis stopped and adds that this is not always the cause, as the solver's README explains; a unit test checks that none of the six sentences contains "cause" or "because".
- The sum of the reaction forces is not in the criterion. It is there so that an engineer can check equilibrium against the applied loads at a glance; it is compared with the largest single reaction force, so reactions that cancel print as "0".
- Reactions are listed for every node that has a support, also one that only holds the node in the plane (after "Restrain out of plane" the portal frame lists four).
- Test hooks: `analysis-status` (with `data-status`: `analysing`, `analysed`, `issues`, `unstable`, `unsupported`, `overflow`, `failed`; and `data-stale`), `analysis-title`, `analysis-time`, `analysis-warning`, `analysis-where`, `analysis-restrain`, `analysis-retry`; `results` (with `data-stale`, `data-load-case`), `results-stale`, `results-none`, `reactions`, `reaction` (with `data-node`), `reaction-sum`, `node-displacement` (with `data-node`), `member-end-forces` (with `data-member`), `member-end` (with `data-end`), `result-value` (with `data-component`).

Deviations and limits:

No code was needed.
- No debounce and no timeout: a `solve` that never returns would leave "Analysing…" for good (the solver's client has no timeout either, card S9).
- The file names `status.ts` and `runAnalysis.ts` are not `analysisStatus.ts` and `liveAnalysis.ts`, because those differ from `AnalysisStatus.tsx` and `LiveAnalysis.tsx` only in case and the type check refuses that on a case-insensitive file system.
- The Results section is below the Loads section; at 1280 by 720 it starts below the fold unless the panel is scrolled (the status line stays visible).
- With many supports the Results section is long (one card per support); nothing folds it. Card W11 has the results panel.
- `packages/solver/README.md` still says, under "In a Web Worker", that no worker was created in `apps/web` or in a browser. That is no longer so; the package was not edited (out of this card's files). No defect was found in `packages/model` or `packages/solver`.

For W9 (deflected shape and reactions in the viewport): read the results with `shownResults(useAnalysisStore(...).analysis, model)` from `analysis/analysisState.ts`: it returns `{ model, result, stale }` or `null`; `result.loadCases[activeLoadCaseId(model, loadCaseId)]` is the load case (check with `Object.hasOwn`: a load case added after the solve has no entry yet). A check that needs results should take them through `shownResults` too, so that a utilization is never coloured from the results of another model.
