# PX-03.6 Evidence against the reference

## Spec

Pitch card T6 of `docs/plan/pitch-plan.md` (tasks and grading), approved by the owner with the plan on 2026-11-18. What: Evidence: the submission's numbers compared with the reference within tolerances. Why: the showcase of 2026-12-16 for the owner's pitch and thesis defense on 2027-01-01. Review station: yes (the full bar: a wrong number or a false statement fails the card). The foreman writes this card's acceptance criteria here before its build starts.

Foreman's note (2026-11-18): this card runs ahead of its listed dependencies (the submission of card T5) in the platform lane, because the evidence is a pure function of a task and a submission and shares no files with the cards in core and web. The shape of a submission is defined here and card T5 stores it.

Acceptance criteria (foreman, 2026-11-18):
1. A new workspace package `packages/grader` (`@bridle/grader`, TypeScript, set up like `packages/tasks`, depending on `@bridle/model`, `@bridle/solver` and `@bridle/tasks` by `workspace:*`; `factory/lanes.json` already gives `packages/grader/` to platform) defines a `Submission`: the task id, the learner's model, the typed answers by answer id (numbers in the display unit, or absent), the written justification, and the time. `validateSubmission` reports a wrong task id, an answer id the task does not have, a non-finite number and a model that does not parse.
2. `buildEvidence(task, submission)` returns the evidence as plain, deterministic data (no dates, no random order), made of these parts:
   a. Model state: whether `validateModel` accepts the learner's model (with its issues), and whether `solve` solves it, refuses it as unstable (with the node and direction) or as not supported.
   b. Fixed parts: each part the task fixes that the learner's model lacks or has changed (compared field by field with the starting model), named.
   c. Supports: for each node that has a support in the reference model or in the learner's model, the six restraints of both and whether they agree; restraints that only hold a planar model in its plane (uy, rx, rz on a model lying in one X-Z plane) are compared separately and their absence or presence is not counted as a difference in the support conditions the task asks for.
   d. Loads: for the task's load case, the resultant of the applied loads of both models (three force components, and the moment about the origin), whether they agree within 1 percent, and a per-load comparison where a load of the reference has a counterpart on the same node or on a member between the same two nodes.
   e. Answers: for each required answer of the task: the learner's typed value; the reference value; the value the solver computes for the learner's own model for the same quantity (the member found by its end nodes, not by its id); the tolerance used; and a verdict among `correct` (typed value within tolerance of the reference), `consistent-with-own-model` (outside the reference's tolerance but within tolerance of the value from the learner's own model, which tells a modelling error from a reading error), `incorrect`, `missing` and `pending` (the reference is not available yet). The tolerance rule is the one `packages/tasks` states: |answer − reference| ≤ max(relative × |reference|, absolute), in the display unit; a signed answer is compared with its sign, an unsigned one by magnitude.
   f. Requirements: each design requirement of the task evaluated on the learner's model (value, allowable, ratio, satisfied).
   g. Section choice, for a task that has one: the section chosen, whether it is in the allowed list, whether it meets the requirements, and whether a lighter allowed section also meets them (lighter by cross-section area).
   For a task whose answers depend on the learner's design choice (task (c)), the reference value of an answer is the value computed for the reference model with the learner's chosen section, as the task's data says.
3. `summarizeEvidence(evidence)` returns counts and flags without prose (how many answers are in each verdict, whether the model solved, the numbers of differences in fixed parts, supports and loads, whether the requirements are met), for the interface and for the AI prompt of card T7.
4. Tests for each of the three tasks: the reference model with the reference answers gives no difference and every answer `correct` (except the pending one of task (c)); and each of these gives exactly the expected evidence: a pinned base where the task asks for a fixed one; a missing load; a load of the wrong size; a load on the wrong member or node; a typed answer 5 percent off; a sign error on a signed answer; an answer left out; an answer typed from the learner's own wrong model; an unstable model; a changed fixed part; members drawn with other ids than the reference's; the out-of-plane restraints added or not; for task (c) a section that fails the limit, the lightest that passes, and a heavier one than needed. A test shows that evidence built twice from the same input is identical, and that it survives `JSON.stringify` and `JSON.parse` unchanged.
5. The README defines every field of the evidence and each verdict in one sentence each, with one worked example; `pnpm check` is 7/7 and `bash tools/test/lanes.test.sh` passes.
Files: `packages/grader/` (new), `pnpm-lock.yaml`. Out of scope: storing submissions (T5), the AI feedback (T7), any interface (T8, T10), the stress reference of task (c) (after card S8).

**Matching rules**

- Nodes by position, within `NODE_MATCH_TOLERANCE` = 1e-6 m; each node matched once, the nearest first, the first in the learner's order among equally near ones.
- Members by their two end nodes in either direction (`reversed`); each matched once.
- A member's "start" or "end" in an answer's source is resolved through the node: the "end" of reference member A-C is the end at C. The solver's end action there is expressed in the reference member's local axes (the vector is turned to global axes with the learner's member's axes and projected on the reference member's axis), so a member drawn the other way or with another roll angle gives the value with the reference's sign. When the two members have the same three axis vectors the solver's number is used as it is.
- Supports by node; loads by the node or member they act on, summed per kind and target; releases compared at the node.
- Sections, materials and load cases by id (they have no position, and their ids come from the starting model).
- Fixed parts by list and id, compared field by field with the starting model, numbers exactly; a missing node or member with a counterpart at the same place names it in `counterpartId`.

**Limits of the matching** (all in the README)

- A member split by an extra node has no matched member. Answers read at an end of it are still found, through the one piece that ends at the node and lies on the reference member's axis (`ownModelLocation.piece`); with two such pieces or none the own-model value is `member-not-found`. Loads on the pieces are not matched (the reference's load is `missing`, the learner's are `extra`; only the resultant agrees), the pieces' section and other properties are not compared, and a section choice on a split member is `member-missing`.
- One member where the reference has two is an extra member. A node moved by more than 1e-6 m is not matched. A model moved or turned as a whole is not recognised.

**Decisions**

1. The verdicts are tested in this order: `missing` (nothing typed), `pending` (no reference value), `correct`, `consistent-with-own-model`, `incorrect`. So an answer left out is `missing` also when its reference is pending. The allowance for the own-model comparison is taken from the own-model value: max(relative × |own|, absolute).
2. `correct` is about the typed number only: reference answers typed beside an unstable or a wrong model are `correct`; the other parts say what the model is.
3. `signError` (an addition): `true` for a signed answer that is `incorrect` and would be `correct` or `consistent-with-own-model` with the opposite sign.
4. The reference value for task (c) is computed by `computeAnswers` for the reference model with the chosen section when one allowed section is on both members (`referenceBasis: "reference-model-with-chosen-section"`); with mixed sections, a section outside the list, a missing member or an unreadable model it is the reference model as it is (`"reference-model"`).
5. Loads agree when the length of the difference vector is at most max(0.01 × the length of the reference's vector, 1e-9), separately for force and moment; the resultant's moment is about the global origin. Per-load: nodal loads by their six components, uniform loads by their force per unit length in global axes, point loads by force and by moment about the reference member's start node.
6. Planarity is read from the reference model alone (all nodes at one y within 1e-6 m).
7. Requirements are reported in mm; `ratio` and `satisfied` are computed in metres as `@bridle/tasks` does.
8. `buildEvidence` replaces −0 by 0 (a product such as −15 × 0), because `JSON.stringify` writes −0 as 0.
9. `buildEvidence` does not throw for any value: an unreadable model leaves `matching`, `fixedParts`, `supports` and `loads` `null`, and the typed answers are still compared with the reference.

#### Rework loop 1

Rework: the review's one finding (numbers that are not finite reach the evidence) and its observation on an own-model value of zero were fixed first; nothing else was changed. 2026-11-18, the same agent.

**What changed**

- New file `packages/grader/src/range.ts`: `inRange(value)` (finite, and magnitude at most `VALUE_BOUND`), `allInRange(values)`, and `nonFinitePaths(data)`, which lists the paths of the numbers in plain data that are not finite. `inRange` is the one helper every number computed from a model passes before it is stored.
- `types.ts`: the constant `VALUE_BOUND = 1e100`; two new values of `ValueStatus`, `out-of-range` and `no-loads`; a new field `learnerOutOfRangeLoadIds` on a load comparison; the header comment and the comment of `unresolvedLoadIds` corrected.
- `answers.ts`, `answerEvidence`: a converted own-model value that is not `inRange` is not stored: `ownModelStatus: "out-of-range"`, `ownModel` and `ownModelLocation` `null`, so the verdict is the one of an own model without a value. `referenceValues` gives `out-of-range` the same way for a reference value. `ownModelValue` takes a new argument `loaded` and returns `no-loads` without it.
- `requirements.ts`: a value in mm or a ratio that is not `inRange` gives `status: "out-of-range"` with `value`, `ratio` and `satisfied` `null`. `sectionChoice.ts`: a requirement check of an allowed section whose numbers are not `inRange` is left out.
- `loads.ts`, `resolveLoads`: a load with a component of its force, its own moment, its point of action, its force per unit length or its moment about the origin (r × F) that is not `inRange` is unresolved: in `unresolvedIds`, in no resultant and no sum, and returned under `outOfRange` with its node or member; `compareLoads` names it in the comparison of that node or member (`learnerOutOfRangeLoadIds`). New `hasAppliedLoad(model, loadCaseId)`.
- `evidence.ts`: `buildEvidence` passes `hasAppliedLoad` of the learner's model to `ownModelValue`.
- `README.md`: the three sentences the review named are rewritten (the rules "Finite numbers" and "Equal to its JSON copy", and the sentence on what a verdict follows from); the bound and its reason; the two statuses; the paragraph on a model without an applied load; the rows of `unresolvedLoadIds`, `learnerOutOfRangeLoadIds`, `referenceStatus`, the requirement's `status` and `options[].requirements`; two lines under Limits.

**The bound and its reason.** `VALUE_BOUND = 1e100`, applied to an answer's value in its display unit, a requirement's value in mm and its ratio, and every component of a resolved load. It is far above any quantity of a structure in kN, kN·m, m or mm, and far enough below the largest double (about 1.8e308) that what the evidence then computes from bounded numbers stays finite: the difference from a typed value of any finite size (the largest double plus 1e100 is the largest double), an allowance, the product of two of them in r × F (at most 1e200), and the sum of the loads of a model. A value exactly at the bound is accepted (tested).

**The decision on an own-model value of zero.** A learner's model with no applied load in the task's load case (no load, loads of zero, loads only in another load case, or only unresolved loads) gives zero for every result whatever the model is, so zero is not a reading of it: every own-model value is then `no-loads` and `null`, and no typed value is `consistent-with-own-model`. The rule is about the loads, not the value: a loaded model whose value is zero keeps it (the moment at a pinned base: typed 0 and 0.0499 are `consistent-with-own-model`, 0.0501 is `incorrect`, tested). The requirements (part f) are not changed: an unloaded model still has a requirement value of 0 and `satisfied: true`, which the review lists as an observation for T7. This changes one statement of the first pass: in the scenario "missing load, reference answers" of task (a) the answers are still `correct`, and `ownModel` is now `null` with `ownModelStatus: "no-loads"`, not 0.

**Observations (advisory; none fails the card)**

For T4 (the workspace in task mode), which can keep most of this from being submitted:

- Keep the fixed parts under their ids: redrawing or splitting a fixed member is reported as `missing` although the structure is right (tasks (b) and (c)). Task (a) does not fix the members, so there a student can split one.
- Offer only the task's load case, or warn before submitting when it carries no load: the right loads in a second load case give own values of 0, and with the reference values typed all answers are `correct`.
- Warn about a node no member uses: the solver reports `unstable` at that node, and the degree of freedom it names (`C.ux` for a loose node, also for a missing `ux` at A) is not a diagnosis.
- Bound the numbers a field accepts (finding 1).

For T5 (storing a submission):

- Pass the model as an object: a model sent as its JSON text is `invalid-model`. Convert typed text to numbers: the string `"45"` is `invalid-shape` and its verdict is `missing`, not `incorrect`.
- Refuse a submission for which `validateSubmission` returns an issue; `buildEvidence` builds evidence for it all the same.
- The ids of nodes, members and loads, the submission's task id and unknown answer keys are the learner's text and are copied into the evidence without a limit on length or characters: bound them here, because T7 puts the evidence in a prompt.
- The same model with its lists in another order gives own-model values that differ in the last digit (15.609433751647229 against 15.60943375164723): do not compare stored evidence for equality across saves. Bound the size of a model (1003 nodes took 0.5 s).

For T7 (the AI feedback prompt):

- `correct` means only that the typed number is within tolerance of the reference. It stood beside an unstable, invalid, unsupported or empty model, and beside own values of 0, in a dozen of my submissions. The prompt needs the rule the builder gives: credit a reading of the model only when `model.solve` is `solved` and `ownModelDifference ≤ ownModelAllowance`; otherwise say that the number is right and the model does not give it.
- `requirementsMet: true` is about the learner's own model whatever it is: supports on the eaves, a prop at B, or no load in the load case give a sway of 0 and "met". Word a requirement as met only when supports, loads and members show no difference.
- Coincidences are real and frequent: both loads on the left half (moment and deflection), load and stiffness both halved (deflection), supports on A and C (moment 67.5), wind reversed or moved to C (sway within 2 percent). A `correct` beside a load or support difference must be worded as a coincidence, not as mastery.
- `consistent-with-own-model` with `ownModel: 0` accepts any typed value up to the absolute part (0.05): a deflection typed in metres (0.0148) on a model without loads is "consistent". When `ownModel` is 0, word the model's fault, not a correct reading.
- A `missing` load with `learnerTargetId: null` (the member is split or redrawn) while `resultant.agrees` is `true` is not a missing load; neither is a nodal `missing` beside an extra point load at that node's end of a member. But the same pattern on a matched member (point loads for the uniform load) is a real error. The prompt must tell these apart with `learnerTargetId`; the summary's counts alone (`members.missing`, `loads.missing`, `loads.extra`) read as a broken model for a split one. A later card could recognise collinear pieces in `matching` and sum their loads; until then this is the main risk in task (a).
- A fixed member `missing` with a `counterpartId` was replaced, not removed.
- A moved node gives one cause and mixed verdicts (`reaction-a` CWOM, the rest `incorrect` through `node-not-found`): report the moved node first.
- Task (c): `sectionChoice.meetsRequirements` is the reference model with the chosen section; `requirements` is the learner's own model. They disagree when a section's properties were edited (`fixedParts` shows it). With `mixed`, a section outside the list or a split member, `referenceBasis` is `reference-model` and the learner's deflection is judged against `I 400x180`. The stress is `pending`: say nothing about its value.
- Unsigned answers hide directions: a load applied upward, or the wind reversed, leaves magnitudes `correct`.
- Members drawn in the other direction, with other ids or rolled 180° gave no wrong verdict, load status or release comparison in any task.
